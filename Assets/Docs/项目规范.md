# 项目规范

版本：0.7 地图机关子模块协作版
最后更新：2026-10-15
适用范围：SlimeBattle-TapTapGamejam Unity 项目  
文档位置：`Assets/Docs/项目规范.md`

## 1. 文档定位

本文件规定团队共同使用项目文件时的最低约束，不规定成员分工，也不替代策划案。

规范中的词语含义如下：

- **必须**：违反后会导致项目无法稳定协作，或必须先取得团队确认。
- **建议**：默认采用，但遇到实际问题时可以提出修改。
- **待确认**：当前资料不足，不能当作已经确定的规则。

玩法需求、架构和协作规范发生冲突时，按以下顺序处理：

1. 团队在当前对话或会议中最新确认的决定；
2. 最新策划源文档《第一关.docx》的玩法内容；
3. `项目架构.md` 的系统边界和数据所有权；
4. 本文件的协作、质量和版本控制规范；
5. 对应系统设计文档；
6. 仓库内 `Assets/Docs/SlimeBettle设计文档-3.docx` 及其他旧资料；
7. 个人实现习惯。

如果最新策划与 Unity 技术基线、架构边界或协作规范冲突，必须保留冲突记录并提问确认，不能静默选择一方；本条不允许任何人以“策划优先”为由绕过版本控制、安全和审查规范。

没有经过确认的示例、参数和文件名，不得被当作硬性需求提交给其他成员。

## 1.1 方案确认与质量边界

- 遇到多个合理方案、多个选项或会影响后续开发方向的取舍时，必须先说明问题、候选方案、成本、风险和后续影响，再向负责人提问；未得到确认前，不得把建议写入正式架构、公共 API、分工或生产代码。
- 项目目标不是“能运行即可”的最小实现。默认应选择相对更优、可维护、可测试并保留后续扩展边界的方案；如果性能、开发成本、视觉质量、扩展性或联调风险之间存在取舍，必须及时报告并取得确认。
- 纯机械且不改变玩法、架构、公共接口或数据契约的修改，可以在记录假设后执行；仍须保持修改范围可追溯。
- 文档中必须明确标注“已确认”“建议”“待确认”“实现事实”和“未验证”，不得把建议写成决定，也不得把测试夹具写成正式玩法。

## 2. 已确认的开发环境

### 2.1 Unity 与渲染

- Unity 编辑器版本：`2022.3.62f2c1`。
- 所有成员必须使用同一编辑器版本，不能由个人单独升级或降级。
- 当前项目使用 URP 2D 模板和 2D Renderer。
- 输入统一使用新版 Unity Input System Package。
- IDE 不设统一限制；团队中可以使用 VS Code，也可以使用其他能正常打开和调试项目的 IDE。
- 版本控制工具确定使用 Git，远程仓库使用 GitHub；当前主分支为 `master`。
- 三位开发者均使用个人分支开发，通过 Pull Request（PR）合并到 `master`，禁止直接向 `master` 推送。
- 包版本以 `Packages/manifest.json` 与 `Packages/packages-lock.json` 为准。
- 不允许为了个人功能随意新增、升级或删除包。需要变更时，先记录原因、影响范围和回退方式。

### 2.2 尚未确认的环境项

以下内容尚未从团队得到最终决定，在本版本中不作强制假定：

- GitHub 仓库的分支保护、审核人数和权限细节；
- 操作系统是否统一为 Windows；
- IDE 的统一插件、代码格式化和检查规则；IDE 本身不作限制；
- Android SDK、NDK、JDK 和具体构建机；
- Input System 的 Action Map、Binding、命名和输入封装细节；
- Android 屏幕方向、目标分辨率和适配策略；
- 最低 Android 版本、目标设备和性能指标；
- 代码命名空间的最终名称；当前系统设计文档暂定根命名空间为 `SlimeBattle`，正式写代码前需确认是否沿用。

这些项目确认后，必须补写到本节，并在变更记录中说明。

### 2.3 通用文件规则

- 文本文件使用 UTF-8 编码。
- Unity 资产必须保留对应的 `.meta` 文件。
- 不手动编辑 `Library/`、`Temp/`、`Logs/` 和 `UserSettings/` 中的生成内容。
- 不把本机绝对路径、个人密钥、临时导出文件或未经确认的外部插件提交到项目内容中。
- Unity 编辑器、包管理器和构建工具产生的变更，提交前必须检查是否属于预期结果。

现有 Unity 基础设置继续保留。项目玩法内容统一放在 `Assets/Game/` 下；当前的 `SampleScene` 已迁移到 `Assets/Game/Scenes/`。

当前代码目录和命名空间暂不迁移；小智负责 `MapManager`、`MechanismSystem` 以及它们对应的 Authoring、配置、Prefab

### 3.1 场景目录说明

`Assets/Scenes/` 和 `Assets/Game/Scenes/` 在 Unity 中没有功能上的区别。只要位于 `Assets/` 下，Unity 都会将其中的 `.unity` 文件识别为场景资源。

两者的差异只是项目组织约定：

- `Assets/Scenes/` 是 Unity 初始模板常用的默认目录；
- `Assets/Game/Scenes/` 是本项目按玩法内容划分后的正式目录；
- 当前 `SampleScene` 已迁移到 `Assets/Game/Scenes/`，并保留了场景和文件夹的 `.meta` GUID；
- 后续正式关卡、测试场景和开发场景统一放在 `Assets/Game/Scenes/`，不再在两个目录之间分散。

目录规则：

- 新建脚本、预制体、配置和正式场景，优先放入 `Assets/Game/` 对应目录。
- `Assets/Game/Scenes/` 是正式场景和测试场景的规范位置。
- 原 `Assets/Scenes/` 仅为 Unity 初始模板目录，当前已完成迁移，不再存放项目场景。
- 项目规范、架构和设计资料统一放在 `Assets/Docs/`；具体系统设计文档和全局 API 查询表统一放在 `Assets/Docs/Systems/`；候选任务单放在 `Assets/Docs/Tasks/`；根目录 `README.md` 保留为仓库入口。
- 当前策划源文档为 `Assets/Docs/SlimeBettle设计文档-3.docx`；策划文档更新后，先区分已确认规则、暂定规则和图示/文字冲突，再同步到 `项目架构.md` 和受影响的 `Systems/` 文档。旧版策划文档不能覆盖 `-3` 的确认内容。
- `Core` 不存放机关、武器、Actor 或其他具体玩法对象的运行时数据；本项目允许将跨系统的关卡结果规则作为轻量 Core 组件放入 `Core`，该组件只能保存结果阶段/原因和订阅，不得保存武器或史莱姆状态。
- `Assets/Docs/Tasks/` 或 `Assets/Docs/` 下的个人任务单只能作为候选分工和协作说明；未经过负责人确认的任务单不能视为最终分工或公共 API 批准。
- `Art`、`Audio` 和 `UI` 中的原始资源不与运行时状态混放。
- 基础架构目录可以按本规范预先创建；功能专属的更细目录应在实际内容出现时再增加，避免无上限扩张。
- 目录名和资产名应使用英文、数字和下划线，避免空格、全角符号和难以输入的字符。
- 第三方插件放在独立目录，不与 `Assets/Game/` 混合；具体目录待版本控制方案确认后确定。

### 3.2 首关测试范围约束

当前第一张程序测试地图以用户提供的最新《第一关.docx》和会议确认结果为准，包含地形、史莱姆、敌人、守卫、终点洞穴、三条路线，以及食物、熔炉、障碍、陷阱和补给等第一关元素。史莱姆上限为 20；熔炉首版只提供史莱姆引导源，不触发寒冷/炙热状态；守卫不消费食物、温暖或史莱姆状态效果。

第一关成功条件是至少 6 只史莱姆进入终点洞穴；等待窗口结束时仍不足 6 只则失败。旧版护送武器结果链路可以作为现有兼容代码保留，但在最新第一关策划重新确认前，不计入第一关成功条件。通用宠物、通用掉落物、背包、通用事件系统和道具系统不进入本轮；第一关若使用敌人掉落食物，只按局部供给规则实现，不恢复通用掉落系统。三条路线按策划预绘制路线事实实现，不等同于通用动态寻路。

首关放置采用“Unity Grid + Snap Anchor”和独立网格可视化：地图边界内普通格子默认合法，一个普通格子只能有一个玩家放置对象；普通格子重复放置直接拒绝。特殊 Anchor 只允许配置的机关类型，是否替换由 Anchor 配置决定；当前第一关 L/SL 障碍允许替换旧障碍，必须由 `MechanismSystem` 回收旧对象后再提交新对象，替换失败不得丢失旧对象。`PlacementSystem` 只负责模式、预览、格子/Anchor 合法性、占用和确认结果，不直接修改路线、陷阱或 Actor 状态。

## 4. 资产与命名规范

### 4.1 C# 文件与类型

- 一个主要类型对应一个同名 `.cs` 文件。
- 类型、方法、属性和枚举使用 `PascalCase`。
- 私有字段使用 `camelCase`；需要在 Inspector 暴露的字段使用 `[SerializeField] private`，不为了显示而公开字段。
- 常量使用 `PascalCase`，或在团队确认后统一采用既有常量风格。
- 布尔值使用 `is`、`has`、`can`、`should` 等可读前缀。
- 文件名必须与主要类型名称一致。

### 4.2 Unity 资产

推荐使用以下后缀，最终可随美术资源管线调整：

| 类型 | 示例 |
| --- | --- |
| 场景 | `Level_01`、`Test_SlimeMovement` |
| 预制体 | `PF_Slime`、`PF_Mechanism_Water` |
| 配置 | `CFG_Slime_Green`、`CFG_Level_01` |
| 精灵 | `SPR_Slime_Green` |
| 动画控制器 | `AC_Slime` |
| 材质 | `MAT_Ground` |
| 音频 | `SFX_SlimeHit`、`BGM_Level_01` |

后缀只是定位资产用途的建议，不应在团队尚未确认美术导出规则前强行改名既有资源。

### 4.3 ID 与运行时对象

- 配置资产的稳定 ID 必须唯一，并且不能依赖显示名称作为唯一标识。
- 运行时对象需要区分配置 ID 与实例 ID。
- 关卡重开或对象销毁后，旧请求不能作用于新对象。
- ID 的具体类型和生成方式由 `项目架构.md` 的实现决策确定；在确定前不得在多个系统中各自发明格式。

## 5. 场景规范

### 5.1 场景类型

场景名称必须能看出用途：

- `Bootstrap_`：启动或全局初始化场景；是否需要该类型待关卡流程确认。
- `Level_`：正式关卡场景。
- `Test_`：只用于验证一个或一组规则的测试场景。
- `Dev_`：开发过程中的临时组合场景，完成后应删除或转为正式测试场景。

### 5.2 场景层级

正式场景和测试场景都应尽量使用清晰的顶层分组。以下是建议结构，不要求在设计尚未确定时一次性建立所有对象：

```text
SceneRoot
├─ Systems
├─ World
├─ Actors
├─ Interactables
├─ SpawnPoints
├─ Cameras
└─ UI
```

规则：

- 场景只保存场景内容和初始配置，不保存上一局的运行状态。
- 可复用对象优先制作成预制体，不在多个场景中手工复制同一套复杂层级。
- 预制体不得依赖某个场景中的临时对象；需要引用时通过初始化或配置注入。
- 场景对象的初始化不能依赖多个脚本 `Start()` 的偶然执行顺序。
- 场景中必须能看出出生点、目标点、窄路、机关范围等关卡设计标记；标记的具体组件由架构实现决定。
- 正式场景和测试场景分开。测试场景应能快速重现移动、碰撞、机关、死亡、重开等问题。

### 5.2.1 场景组合测试场景

团队可以使用一个独立的场景组合测试场景（当前暂定名为 `FirstLevelComposition_TEST`）合并各模块的场景资源和 Prefab。该场景只用于集成验证，不等同于正式第一关，不自动加入 Build Settings。

必须遵守：

- 当前已确认的首关协作边界为：小智负责 Map 领域（`MapManager` + `MechanismSystem`），小宸负责 Input/Camera/Placement/UI，
  小茶负责 Actors/AI、Actor Manager、Core 接线和集成装配。各自交付 Authoring、Prefab、配置、适配器和独立测试；集成者通过场景引用和公开接口组合，不复制或维护他人系统内部源代码；
- 需要 Inspector 引用的字段使用 `[SerializeField] private`。可以序列化具体 `MonoBehaviour`、`GameObject`、`Transform`、Prefab 和 `ScriptableObject`，不直接序列化由 `LevelContext` 创建的 plain C# Manager；
- Unity 不支持把任意 plain C# 接口作为普通场景引用。接口协作必须由具体 `MonoBehaviour` 适配器或 `ScriptableObject` 配置承载，再在运行时转换为接口；不得通过反射、私有字段或全局单例绕过边界；
- `SceneCompositionRoot`/`LevelSceneInstaller` 只能负责引用校验、依赖注入、场景父节点连接和生命周期清理，不拥有地图、Actor、机关或结果规则的第二份运行时数据；机关正式创建、替换、回收和生命周期仍由小智维护的 `MechanismSystem` 负责；
- 装配顺序必须由明确的 LevelStarted/安装流程驱动。不得依赖多个脚本 `Start()` 的执行先后，也不得在装配组件中重复创建 `LevelContext`、Manager 或 Actor 列表；
- 独立测试可以使用 Mock Backend、占位 Prefab 和模拟事件，但对象、按钮、彩色方块和模拟结果必须标记 `TEST_ONLY`，不能写入正式场景；
- 集成测试场景通过后，必须另行检查正式场景引用、Prefab GUID、Build Settings、重开清理和运行时证据，不能因为 Inspector 引用完整就宣称玩法通过。

推荐的集成测试场景分组为：`MapRoot`、`EntitiesRoot`、`MechanismsRoot`、`PresentationRoot`、`UIRoot` 和 `SystemsRoot`。同一复杂场景或 Prefab 同一时间只能由一人编辑；集成者只修改组合层和适配调用方。

### 5.3 场景与物理约定

碰撞层、标签、Sorting Layer、坐标单位和跳跃/坑的表示方式必须集中记录，不能由各个预制体自行创建近似规则。最终表格待物理方案确定后补充。

## 6. 预制体、配置与表现

- 预制体负责组件组合和默认引用，不负责保存一局游戏的运行数据。
- 配置资产保存设计时规则和数值；运行时生命、目标、冷却、队列位置等数据必须属于对应运行时系统。
- 表现组件可以读取数据、播放动画和特效，但不能自行决定伤害、死亡、出生、过关或失败。
- 美术资源未到位时，可以使用占位精灵、颜色块和占位动画验证规则；占位资源不得改变系统接口。
- 可复用预制体不应直接引用正式场景中的对象。
- 预制体需要新增必需组件时，应在测试场景中验证新旧实例均可正常加载。
- 场景组合所需的跨系统引用优先放在专用装配组件或适配器上；不要让可复用 Prefab 直接引用某个测试场景对象。

## 7. 代码规范

### 7.1 依赖与职责

- 一个类只负责一个清晰的规则或适配职责。
- `MonoBehaviour` 用于连接 Unity 场景、物理、输入和表现；纯规则可以使用普通 C# 类。
- 规则数据只能由其所属系统修改，其他系统通过公开方法或命令请求修改。
- 已经发生的结果可以用类型明确的事件通知多个观察者。
- UI、动画、音效和特效不能成为规则执行的前置条件。
- 不在每帧或每个物理步中使用 `FindObjectOfType`、全场无条件查找或字符串查找来连接系统。
- 不使用未经约定的全局静态状态保存关卡运行数据。

### 7.2 Unity 生命周期

- `Awake` 只做本组件引用缓存和本地初始化。
- 系统之间的连接由明确的初始化流程完成，不依赖脚本执行顺序。
- `Update`、`FixedUpdate` 和协程的使用必须能说明其时间语义；行为思考、物理移动和表现刷新不能混为一谈。
- 暂停、重开、关卡结束和场景卸载时，必须清理订阅、计时器、队列和待处理请求。
- 事件监听在启用时注册，在禁用或销毁时取消。

### 7.3 修改现有代码

- 每次修改都应能对应到需求、缺陷或架构决策。
- 不在处理功能时顺手重命名无关变量、重排无关文件或重构未出现问题的模块。
- 新增公共方法时，必须说明调用方、参数含义、失败结果和生命周期要求。
- 变更公共数据结构或事件时，同时更新 `项目架构.md` 的接口记录。

## 8. GitHub 协作与同步规则

GitHub 远程仓库和主分支已经确定。本节规定三位开发者使用个人分支、同步主分支和通过 PR 协作的流程：

- 同一时间只能由一个人编辑同一个场景或同一个复杂预制体。
- 不直接覆盖其他人的未确认修改。
- 场景、预制体和配置发生结构变化时，修改者应在协作消息或变更记录中说明影响范围。
- 合并前先打开受影响场景，确认没有丢失引用、重复对象或脚本编译错误。
- 公共接口变化必须先通知受影响的调用方，再提交依赖该接口的实现。
- 跨系统事件的发布者和观察者变化必须先更新对应系统文档及 `99-全局API查询表.md`；武器事件只能由 `MechanismSystem` 发布，关卡结果事件只能由 Core 结果规则组件确认。
- 任何临时调试开关、测试对象和日志都要标明用途；测试结束后删除，或明确保留为测试内容。

### 8.1 分支命名

- `master` 是团队主分支，禁止直接推送；
- 每位开发者使用自己的个人绰号作为分支名前缀；
- 每个功能、问题或文档任务使用独立分支，不多人共用同一个开发分支；
- 分支名只使用英文小写字母、数字和短横线。

分支格式：

```text
<nickname>/<type>-<task>
```

示例：

```text
kcz/feat/game-root
slime/fix/level-restart
fox/docs/project-architecture
```

类型约定：`feat` 新功能，`fix` 问题修复，`docs` 文档修改，`refactor` 重构，`chore` 工程配置。

### 8.2 开始任务与同步

开始新任务前，先同步最新的主分支，再创建个人分支：

```powershell
git switch master
git pull --ff-only origin master
git switch -c <nickname>/<type>-<task>
```

创建或更新 PR 前，个人分支使用 rebase 同步主分支：

```powershell
git fetch origin
git rebase origin/master
```

发生冲突时，解决冲突后执行 `git add <已解决的文件>` 和 `git rebase --continue`。已经推送过的个人分支在 rebase 后只能使用 `git push --force-with-lease origin <个人分支>`，禁止对 `master` 使用强制推送。

### 8.3 提交与 PR

提交应当保持小而清晰，一个提交尽量只表达一个完整意图。推送个人分支并创建 PR：

```powershell
git add <需要提交的文件>
git commit -m "feat: implement game root"
git push -u origin <nickname>/<type>-<task>
```

创建 PR 时：

- `base` 必须选择 `master`，`compare` 选择自己的个人分支；
- PR 标题说明实际修改内容，例如 `feat: implement level manager`；
- 至少邀请另一位开发者审核；
- PR 描述必须包含修改目的、主要改动、验证方式和已知风险；
- 涉及场景、Prefab、UI 或美术效果的修改，应附截图或简短演示；
- 未完成的工作使用 Draft PR，不直接请求合并。

### 8.4 审核与合并

- Unity 编译错误、受影响场景验证失败或必要测试未通过，不合并 PR；
- 不在 PR 中混入无关功能、格式化或临时调试文件；
- 推荐使用 Squash and merge，将一个任务压缩为一个清晰提交；
- PR 合并后删除远程个人分支；
- 合并后所有人重新同步 `master`，再开始下一个任务。

### 8.5 Unity 文件协作

- 尽量不要让多人同时编辑同一个 `.unity` 场景或 `.prefab` 文件；
- 需要修改公共场景时，先在协作消息中说明修改范围，避免产生难以合并的序列化冲突；
- 场景对象按本规范的场景层级放入对应 Root 容器；
- 合并前打开受影响场景，确认没有丢失引用、重复对象或脚本编译错误；
- 不提交 `Library/`、`Temp/`、`Logs/`、`UserSettings/` 等 Unity 生成目录；
- `.vscode/` 是个人本地配置，不作为团队共享内容提交；
- 公共接口变化必须先通知受影响的调用方，再提交依赖该接口的实现。

## 9. 最低验收标准

一个功能可以交给团队继续使用前，至少满足：

1. Unity 编辑器无新增编译错误。
2. 受影响场景可以打开，关键引用不丢失。
3. 有一个可重复的测试步骤或测试场景。
4. 暂停、重开和销毁流程没有遗留事件、计时器或运行时对象。
5. 功能不依赖镜头是否看见、动画是否播放或特效是否成功。
6. 若涉及 Android 行为，必须在实际目标设备或明确说明的替代环境中验证；编辑器通过不等于真机通过。
7. 代码、配置或公共接口发生变化时，相关架构说明已经同步。

涉及第一张地图的 PR 还必须说明：三条路线事实和节点来源、普通格子与 L/SL Anchor 的放置边界及替换策略、守卫是否被状态系统排除、熔炉是否保持引导源模式、终点统计/等待窗口来源，以及是否只完成了测试夹具而未接入正式关卡。
