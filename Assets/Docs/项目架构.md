# 项目架构

版本：0.6 第一关策划对齐与锚点放置版
最后更新：2026-10-14
适用范围：SlimeBattle-TapTapGamejam Unity 项目
状态：架构重整后暂定

## 1. 文档定位

本文件说明游戏需求如何拆成系统、系统如何拥有数据以及运行时信息如何流动。它规定边界，不提前锁死所有算法、物理实现和表现资源。

当前确认优先级为：

1. 当前对话中已经确认的架构边界；
2. 最新策划文档《第一关.docx》（本次由负责人提供；若纳入仓库，建议保存为 `Assets/Docs/第一关.docx`）；
3. `Assets/Docs/Systems/` 中对应系统文档；
4. 仓库内 `Assets/Docs/SlimeBettle设计文档-3.docx` 及其他旧策划/旧架构草稿中的可复用建议。

策划文档中的暂定数值、图示冲突和没有成功条件的内容不能直接变成硬编码规则。

## 2. 需求分析

当前项目需要支持一个二维史莱姆引导与对抗的最小可玩闭环：玩家观察关卡，角色根据局部信息自主决策，玩家通过放置机关改变条件，角色移动、攻击、受伤或死亡，Core 结果规则确认关卡结果，玩家可以重开关卡。

在玩法细节尚未全部确认前，架构必须先保证以下能力：

- 加载关卡并建立独立的 LevelContext；
- 从场景和 Tilemap 读取地图、边界、出生点、目标点以及地形/区域语义数据；
- 通过 SlimeManager、EnemyManager 和 GuardManager 管理不同类型 Actor 的生命周期；
- 让每个 Actor 持有自己的生命、状态、感知、决策树和状态机；
- 让决策树只选择行动意图，状态机负责行动过程；
- 让攻击、治疗、自残、持续伤害和机关伤害都可以提交统一效果请求；
- 让 StatusManager 统一结算生命和移动相关状态；
- 让 MovementSystem 查询状态修正后执行实际移动；
- 让 UI 和表现读取快照、监听结果，但不拥有玩法规则；
- 让成功、失败、暂停、重开和卸载具有一致的生命周期。

### 2.1 第一关的策划范围与验收口径

以下内容以最新策划文档 `第一关.docx` 为第一关玩法基线；Unity 场景、组件和数据结构是对该文档的实现翻译，不迁移到其他引擎：

- 史莱姆上限为 20；
- 第一关包含史莱姆、敌人、守卫、地形、终点洞穴以及三条可选择路线；
- 玩家通过食物、熔炉、障碍、陷阱和补给等环境元素影响史莱姆，不能直接拥有或直接操控某个 Actor；
- 熔炉首关只作为引导源，不向 `StatusManager` 申请寒冷/炙热状态；守卫不消费食物、温暖或史莱姆状态效果；
- 第一关的路线、障碍点和陷阱点由场景作者按策划图示配置。路线选择、路线阻断和陷阱关联属于关卡规则/对应运行时模块，不由 `MapManager` 或 `PlacementSystem` 私自推导；
- 第一关成功条件以“至少 6 只史莱姆进入终点洞穴”为准；等待窗口结束后仍不足 6 只则失败。旧版“护送武器抵达终点”的结果口径不再作为本版第一关验收条件；现有武器代码保留为兼容/后续扩展，不能反向覆盖最新策划；
- 宠物、通用掉落物、背包、通用事件系统和道具系统不进入本轮通用架构；如果第一关使用敌人掉落食物，只能作为本关局部供给规则，不得借此恢复完整掉落系统；
- 第一周目的寒冷和炙热效果暂不实现，但地形及其已经确认的移动/空间语义仍属于第一关范围。

史莱姆在不同状态下的完整行为优先级尚待策划补充。本轮按系统设计文档已有行为输入实现，不把未确认优先级写成最终规则。“先进先出”先作为待策划问题记录，暂不固化为公共 API 或通用算法。

## 3. 总体结构

```text
GameRoot
  └─ LevelManager
       └─ LevelContext + LevelEventBus
            ├─ ConfigSystem
            ├─ MapManager
            ├─ SlimeManager
            │    ├─ SlimeActor × N
            │    └─ SlimeGroupActor × N
            ├─ EnemyManager
            │    └─ EnemyActor × N
            ├─ GuardManager
            │    └─ GuardActor × N
            ├─ MovementSystem
            ├─ StatusManager
            ├─ Core 关卡结果规则组件（非独立系统）
            ├─ MechanismSystem
            ├─ PassageSystem（窄路规则待确认）
            └─ Input / Placement / Camera / UI / Presentation
```

### 3.1 LevelContext 的职责

LevelContext 是当前关卡的依赖边界和生命周期容器。它负责创建、连接、暂停、恢复和销毁关卡级服务，但不替 Manager 或 Actor 保存第二份运行时数据。

LevelContext 至少持有：

- ConfigSystem 的当前配置查询入口；
- MapManager；
- SlimeManager、EnemyManager、GuardManager；
- MovementSystem；
- StatusManager；
- MechanismSystem；
- Core 关卡结果规则组件（随 LevelContext 生命周期创建和销毁，不作为独立 Manager）；
- 当前关卡的 LevelEventBus。

每个 Manager 都是独立系统文档中的公共模块，但不能脱离 LevelContext 成为跨关卡单例。

### 3.2 Actors 模块

Actors 模块包含个体和群体级自主决策生物：

- ActorCore：身份、阵营、生命和公共运行时数据；
- ActorDecisionTree：感知与行动意图；
- ActorStateMachine：行动执行、攻击时机、暂停和中断；
- SlimeActor、EnemyActor、GuardActor：具体个体行为；
- SlimeGroupActor：史莱姆群体行为，不拥有成员生命的第二份副本。

Manager 创建和驱动 Actor，Actor 自己拥有运行时数据。这个分离避免把“生成销毁”和“个体行为”混在同一个大型系统中。

## 4. 主要系统职责

### 4.1 核心与目标

GameRoot 负责应用级初始化和入口；LevelManager 负责场景加载、重开、暂停和关卡阶段；LevelContext 负责本局引用和 EventBus；Core 关卡结果规则组件只聚合已发生的结果事件并确认成功/失败。它不拥有武器、史莱姆或其他玩法运行时数据。

`LevelManager` 可以接收 Core 结果规则发布的 `LevelSucceededEvent` / `LevelFailedEvent` 并推进关卡阶段，但不复制胜负规则。`GameRoot` 不接收当前关卡的玩法事件，也不保存关卡结果。

### 4.2 配置

ConfigSystem 提供 ScriptableObject 配置和校验。配置只描述设计时数据，不保存本局生命、状态、冷却、群体成员和目标。

架构预留 `TerrainConfig` 作为地形设计数据：描述 `TerrainId`、可通行性、连续移动修正以及进入/离开效果引用。具体字段和默认值在 ConfigSystem 设计冻结时确认；地形配置不保存某个关卡中某个格子的运行时状态。

### 4.3 四个 LevelContext Manager

| Manager | 负责 | 不负责 |
| --- | --- | --- |
| SlimeManager | SlimeActor、SlimeGroupActor 的生成、索引、驱动、销毁 | 不决定每只史莱姆的具体行为，不结算效果 |
| EnemyManager | EnemyActor 的生成、索引、驱动、销毁 | 不决定通用攻击规则，不直接扣血 |
| GuardManager | GuardActor 的生成、索引、驱动、销毁和指令入口 | 不解析原始输入，不直接改 Transform |
| MapManager | 场景地图绑定、道路/地形/区域/地图点查询、边界、静态阻挡识别和区域转移事实 | 不执行位移，不创建动态地图对象，不决定角色行动或结算效果 |

### 4.4 移动

MovementSystem 接收 ActorStateMachine、InputSystem 或其他合法调用方的移动请求，查询 MapManager 的空间事实和地形移速修正、查询 StatusManager 的 Actor 状态修正，然后执行位置变化、阻挡、碰撞和接触结果。MovementSystem 将刚体的实际位置同步给 MapManager；MapManager 据此发布区域进入/离开事实。

### 4.5 生命与状态

StatusManager 是效果和状态的唯一统一入口。Actor 持有自己的生命与状态数据，StatusManager 持有规则和计时，并通过 ActorCore 的效果接收契约修改目标。

StatusManager 负责 Actor 伤害、治疗、状态计时、易伤、控制、移速/攻速修正等效果，以及向 MovementSystem 提供 Actor 状态修正。首关不启用寒冷/炙热状态；熔炉不向 StatusManager 提交温度效果。守卫不消费食物、温暖或史莱姆状态修正。地形移速仍由 MovementSystem 从地图查询结果读取。击退待 MovementSystem 提供冲量接口后接入。StatusManager 不选择攻击目标，不处理攻击前摇和命中区域。

### 4.6 攻击行为

本架构不设置独立战斗系统。攻击是 Actor 的一种 Action：

```text
Perception
  → ActorDecisionTree
  → AttackIntent
  → ActorStateMachine / AttackAction
  → StatusManager.ApplyEffect
  → 目标 Actor 生命或状态变化
```

决策树负责“是否尝试攻击和攻击谁”；状态机负责攻击前摇、命中时机、后摇和打断；AttackAction 负责在命中时机做一次最终校验并提交 EffectRequest。攻击的生命变化不由决策树、动画或目标 Manager 直接完成。

治疗、自残、持续伤害和机关伤害可直接调用 StatusManager，不强行经过攻击流程。

### 4.7 机关、玩家和表现

MechanismSystem 负责动态环境元素及其运行时状态。首关的食物、仅作引导源的熔炉和障碍由它拥有；护送武器代码若继续保留，也只能由它拥有运行时状态，不能重新归入结果规则组件。陷阱、补给和路线阻断的具体运行时归属必须依据已确认接口接入，不得让地图或 UI 直接创建和结算。

PlacementSystem 采用“Unity Grid + 特殊点位 Snap Anchor”：普通网格格子负责坐标吸附和单格占用；特殊 Anchor 负责策划指定的 L1/L2/L3、SL1/SL2/SL3 等不可由普通格子推导的点位规则。普通格子重复放置直接拒绝；Anchor 是否允许替换由 Anchor 配置决定，当前第一关的 L/SL 障碍放置允许替换旧障碍，并要求通过 MechanismSystem 回收旧对象后再完成新放置。PlacementSystem 不直接修改路线、陷阱或 Actor 状态。

InputSystem 使用新版 Unity Input System Package，把设备输入转换为语义指令；CameraSystem 负责视图；UISystem 和 PresentationSystem 只消费状态与已发生事件。PassageSystem 是否作为独立系统、以及窄路/通道的具体规则，仍待确认。

### 4.8 Core 结果规则与旧武器链路

Core 层保留轻量的关卡结果规则组件，而不是独立的 `ObjectiveSystem` 系统。它只聚合当前关卡已经发生的事实，维护一次性结果快照，并把最终结果交给 `LevelManager` 推进生命周期。

第一关当前应优先接入“史莱姆进入终点洞穴数量”和等待窗口事实：达到 6 只发布成功，窗口结束仍不足 6 只发布失败。史莱姆死亡、终点进入、等待窗口结束等事实由其实际拥有者发布；Core 不直接读取 Actor 私有字段，也不创建或销毁对象。

现有 `MechanismSystem` 的护送武器、`WeaponDamagedEvent`、`WeaponDestroyedEvent` 和 `WeaponReachedGoalEvent` 属于已存在的兼容/后续扩展链路。它们可以继续作为公开事实，但在最新第一关策划没有重新纳入前，不得作为第一关成功条件；是否清理、保留或复用于其他关卡，单独作为后续设计任务处理。

## 5. 数据所有权

```text
ConfigSystem
  └─ 设计时配置，只读

Actor
  └─ 自身生命、状态、位置快照、目标和 AI 运行时数据

Manager
  └─ 同类型 Actor 的集合、索引、生命周期和聚合快照

StatusManager
  └─ 效果规则、状态计时、修正查询和效果结果

MapManager
  └─ 场景地图资源引用、静态地形/区域语义、空间事实和查询缓存

MovementSystem
  └─ 移动请求、执行进度、碰撞和接触事实

MechanismSystem
  └─ 食物、熔炉、障碍及已确认机关运行时数据；护送武器若启用也只归此处

Core 关卡结果规则组件
  └─ 关卡结果阶段、原因和只读结果快照；不拥有武器或史莱姆数据
```

禁止两个系统各自维护同一生命、状态、位置或群体成员的可写副本。需要跨系统协作时使用公共查询、命令和结果事件。

## 6. 关键数据流

### 6.1 移动

```text
Input / ActorDecisionTree
  → ActorStateMachine
  → MovementSystem
  → StatusManager 查询移动修正
  → MapManager 查询空间事实
  → Actor 位置变化
  → MovementResult / MovementBlockedEvent
  → MapManager 比较区域成员关系并发布 MapAreaEntered/ExitedEvent
```

### 6.2 生命与状态

```text
Actor Action / 机关 / 环境 / 目标规则
  → EffectRequest
  → StatusManager
  → Target Actor 的生命或状态变化
  → EffectApplied / HealthChanged / ActorDied

地图区域进入/离开
  → MapManager 发布 MapAreaEntered/ExitedEvent
  → StatusManager 根据区域类型和配置申请或解除状态/效果
```

这里传递的是效果请求，不是把 Actor A 的生命值直接传给 Actor B。自残和治疗只是 TargetActorId 等于 A 的合法效果请求。

### 6.3 群体

```text
SlimeActor 的目标变化
  → SlimeManager
  → SlimeGroupActor 形成或更新
  → 群体上下文返回成员 Actor
  → 个体 DecisionTree / StateMachine
```

群体拥有关系和策略，不拥有成员生命、状态和碰撞体。

### 6.4 地形与环境

```text
场景 Tilemap / 地形语义数据
  → LevelSceneInstaller 或同类场景适配器绑定
  → MapManager 建立空间与地形查询
  → MovementSystem 查询目标位置的 TerrainId / 可通行性
  → 合并 TerrainConfig 的地形修正与 StatusManager 的角色修正
  → MovementResult / MovementBlockedEvent
  → 进入/离开地形事实
  → StatusManager 处理持续性状态或一次性效果
```

视觉 Tilemap 只负责显示；碰撞 Tilemap 或碰撞组件提供物理阻挡；地形语义数据提供 `TerrainId`、区域标签和效果引用。三者可以使用同一套关卡资源组织，但不能让视觉层直接承担玩法判定。动态食物、火炉和可移动障碍仍由 MechanismSystem 管理，并通过公开接口改变可查询的环境事实。

### 6.5 网格与 Anchor 放置

```text
InputSystem 屏幕位置事实
  → CameraSystem.ScreenToWorld
  → Unity Grid 的世界坐标/格子坐标转换
  → PlacementSystem 查询普通格子或策划 Anchor
  → PlacementGridView 显示当前放置状态
  → MechanismSystem 创建、替换或回收食物/熔炉/障碍
  → PlacementConfirmedEvent
```

首关采用 Unity Grid（或等价的场景 Grid Authoring）作为坐标服务，并由独立 `PlacementGridView` 只在进入放置状态时显示网格。地图边界内的普通格子默认合法，一个格子只允许一个玩家放置对象；普通格子重复放置直接拒绝。策划指定的 Anchor 是额外的点位白名单，不由数学网格自动生成；只有配置允许的机关才能在该 Anchor 放置。当前第一关 L/SL Anchor 的障碍替换规则为：新障碍放置成功前，先由 MechanismSystem 回收旧障碍，再提交新障碍；替换失败时不得丢失旧对象。除上述规则外，本轮不做复杂地形兼容、复杂碰撞体积和动态 Actor 占用校验。武器、守卫和史莱姆不是玩家放置对象。

### 6.6 三路线与路线事实

```text
关卡场景路线与分支标记
  → MapManager 提供三条候选路线的只读事实
  → 关卡路线规则根据障碍/陷阱事实筛选可选路线
  → 史莱姆/Actor 决策层消费路线目标
  → 终点洞穴统计进入的史莱姆数量
  → Core 结果规则组件
```

第一关实现三条由策划预先绘制的路线选择，不等同于通用网格寻路。L1/L2/L3 障碍分别影响对应路线的后续选择；已经进入某条路线的史莱姆继续沿当前目标执行，不因新放置自动瞬移或重写历史路径。SL1/SL2/SL3 关联对应路线中的陷阱或特殊点，具体触发效果由陷阱/机关公开接口提供。路线候选的选择时机、同帧阻断和多路线同时可用时的优先级，仍以最新策划和后续确认接口为准。

## 7. 通信规则

- 能明确找到办理者的同步规则使用公开方法调用；
- 需要多个观察者得知的已发生结果使用当前 LevelContext 的 LevelEventBus；
- EventBus 不用于替代命令，不承载可写对象，不跨关卡存在；
- UI、表现和调试工具只能查询快照或提交公开命令；
- 不能通过读取其他系统私有字段完成协作。

## 8. 关卡生命周期

```text
未加载
  → 加载中
  → 初始化
  → 运行中 ⇄ 暂停
  → 结算中
  → 重开或离开
  → 清理
```

初始化顺序：

1. 加载场景和关卡配置；
2. 创建 LevelContext 与 LevelEventBus；
3. 创建并绑定 MapManager；
4. 由 LevelSceneInstaller 或同类场景适配器把视觉 Tilemap、碰撞数据、地形语义和出生点绑定到 MapManager；
5. 创建 SlimeManager、EnemyManager、GuardManager、MovementSystem、StatusManager 和 MechanismSystem；
6. 创建 Core 关卡结果规则组件、输入、镜头、UI、表现及已确认的机关适配；
7. 通过 Manager 生成初始 Actor；
8. UI 主动读取初始快照；
9. 发布 LevelStartedEvent。

暂停时停止 Actor AI、移动、效果计时、群体计时和机关冷却；UI 和必要的暂停输入仍然可用。重开采用重新加载当前场景，旧 LevelContext、Manager、Actor、状态和订阅必须先失效。

## 9. 第一版验收闭环

第一版至少应能完成：

1. 在 Unity 2022.3.62f2c1 下无编译错误；
2. 建立一个包含地形、三条路线、史莱姆、敌人、守卫、机关和终点洞穴的测试关卡；
3. Actor 能通过决策树产生移动或攻击意图；
4. MovementSystem 能执行最小移动；
5. AttackAction 能通过 StatusManager 对目标产生一次伤害；
6. 终点进入统计、等待窗口和“至少 6 只史莱姆”的结果规则可以被 Core 组件观察，并只确认一次结果；

## 10. 小宸 P0 接入记录（2026-10-09）

InputSystem、CameraSystem、UISystem 的首版由场景级 `SlimeBattle.Player.PlayerPresentationRoot` 显式组装，不修改现有 Core 的创建与状态实现。只在场景入口查找一次 Bootstrap 持久化的 LevelManager；日常通过公开方法和其 C# 事件连接。输入在 Running 为 Gameplay，暂停/结算为 UiOnly，其余阶段禁用。

2026-10-10 按反馈修订：输入的 PrimaryAction.ScreenPosition 仅报告屏幕某处发生主要操作；不解释为移动、攻击或放置，不要求 Actor 消费玩家点击。Move / Attack 保留为预留或调试接口，WASD 默认关闭。屏幕/世界坐标使用 Vector2（像素）/ Vector3（XY 玩法平面），未来交互适配层可经 CameraSystem 投影后消费；本 PR 不定义放置规则。地图公开边界由关卡适配层经 MapManager.GetMapBounds 转为 CameraBounds。

输入使用专用 InputEventChannel，Subscribe / Unsubscribe 改用 SlimeBattle.Player.Input.InputSubscriptionToken；先在 PR 与 API 文档通知调用方迁移显式 token 类型。不同输入实例的 token 隔离，Core.LevelEventBus / SubscriptionToken 不变。测试点击只更新 TEST_ONLY_ClickMarker，InputProbe 静止，不模拟正式 Actor 行动。

UI 通过 `IUiSnapshotSource.ReadSnapshot(LevelContext)` 的显示适配层接入各系统只读快照，初始化、阶段变化和最多 5 Hz 重建显示；关卡 ID、阶段始终读取 LevelManager。新增接口、事件、失败与清理约定见 21、23、24 系统文档与 99 API 表；协作通知和示例见 `P0-小宸接入说明.md`。

所有独立测试夹具和场景仅在 `Assets/Game/Tests/PlayerPresentation/`，不更改公共 Bootstrap/SampleScene。测试结果按钮只模拟上游事实，不定义最终胜负规则。本记录不改动其他负责人的 CombatSystem / AttackAction 方案。
