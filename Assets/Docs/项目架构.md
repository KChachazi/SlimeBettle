### 代码现状摘要（2026-10-28）

- Build Settings 启用 `Bootstrap`、`MainMenu`、`FirstLevel`、`Castle`。两个正式关卡当前都配置为护送武器目标；洞穴人数规则保留在旧洞穴配置/测试默认规则中。
- `LevelContext` 创建 `MapManager`、`StatusManager`、`MovementSystem`、`SlimeManager`、`EnemyManager`、`MechanismSystem` 和 `LevelResultRules`；满足配置和场景条件时创建 `GuardManager`。Input、Placement、Camera、UI 与表现由场景级装配组件接入，`PassageSystem` 尚未作为运行时模块接入。
- 史莱姆移动使用 A* 绕开地图/机关阻挡；护送武器按地图配置的固定路线分段移动。两条移动链路的路径策略不同。
- 放置、Anchor 安全替换、拆除、战役库存扣减和关卡重开恢复入场库存快照已有运行时代码。Castle 餐车由 `MechanismSystem` 管理装载及轨道移动。
- 代码/配置差异：奖励表使用 `SecondLevel`，Castle 的 `LevelId` 为 `Castle`，精确 ID 匹配时不会命中奖励；`ObjectiveConfig` 目前只参与配置注册校验，结果规则从 `LevelConfig.ObjectiveKind` 创建，洞穴目标数/等待时长使用代码默认值；陷阱配置资产未注册/消费，首关地刺伤害由场景适配器硬编码。

## 1. 文档定位

本文件说明游戏需求如何拆成系统、系统如何拥有数据以及运行时信息如何流动。它规定边界，不提前锁死所有算法、物理实现和表现资源。

当前确认优先级为：

1. 用户已确认的架构和玩法决定；
2. 当前代码/配置/场景，用于陈述“已经实现什么”；
3. 当前有效策划文档和 `Assets/Docs/Systems/`，用于陈述“设计目标是什么”；
4. 旧策划、旧架构及带日期的任务记录，只作为历史参考。

策划文档中的暂定数值、图示冲突和没有成功条件的内容不能直接变成硬编码规则。

## 2. 需求分析

当前项目需要支持一个二维史莱姆引导与对抗的最小可玩闭环：玩家观察关卡，角色根据局部信息自主决策，玩家通过放置机关改变条件，角色移动、攻击、受伤或死亡，Core 结果规则确认关卡结果，玩家可以重开关卡。

在玩法细节尚未全部确认前，架构必须先保证以下能力：

- 加载关卡并建立独立的 LevelContext；
- 从场景和 Tilemap 读取地图、边界、出生点、目标点以及地形/区域语义数据；
- 通过 SlimeManager、EnemyManager 和 GuardManager 管理不同类型 Actor 的生命周期；
- 让每个 Actor 持有自己的生命、状态、感知、决策树和状态机；
- 让决策树只选择行动意图，状态机负责行动过程；
- 让攻击、治疗、自残、持续伤害和机关伤害都可以提交统一效果请求；
- 让 StatusManager 统一结算生命和移动相关状态；
- 让 MovementSystem 查询状态修正后执行实际移动；
- 让 UI 和表现读取快照、监听结果，但不拥有玩法规则；
- 让成功、失败、暂停、重开和卸载具有一致的生命周期。

### 2.1 当前关卡实现与规则边界

- `FirstLevel` 和 `Castle` 的 `LevelConfig.ObjectiveKind` 当前均为 `EscortWeapon`；武器抵达终点成功，武器被摧毁或史莱姆耗尽失败。旧洞穴目标仍可由 `FirstLevel_CaveLegacy_Test` 配置使用。
- 史莱姆最大数量为 20；两关地图各有 20 个史莱姆出生点，关卡组合按战役数量使用编号靠前的点位。
- 玩家通过食物、熔炉和障碍影响场上行为；放置库存由战役账本管理，同时在场数量由关卡配置限制。Actor 不属于玩家放置物。
- 史莱姆决策优先级在代码中依次处理害怕逃离、饥饿觅食、寒冷寻温、战斗、普通引导和游走；食物增殖开关在战役配置中关闭。
- 史莱姆使用 A* 网格寻路；护送武器仍沿地图中的固定路线移动。障碍阻断时武器重规划策略与 Actor A* 不同，不能把已实现的 Actor 寻路描述为武器自动绕障。
- 角色攻击与伤害由 Actor 行为和 `StatusManager` 结算；Castle 餐车的装载/轨道交互归 `MechanismSystem`。地刺、宝箱、滚石仍由关卡场景适配器接线。

本节记录代码现状，不替代策划规则。配置资产与代码不一致处见“代码现状摘要”和项目场景/配置说明。

## 3. 总体结构

```text
GameRoot
  └─ LevelManager
       └─ LevelContext + LevelEventBus
            ├─ ConfigSystem
            ├─ Map 领域模块
            │    ├─ MapManager
            │    └─ MechanismSystem
            ├─ SlimeManager
            │    ├─ SlimeActor × N
            │    └─ SlimeGroupActor × N
            ├─ EnemyManager
            │    └─ EnemyActor × N
            ├─ GuardManager
            │    └─ GuardActor × N
            ├─ MovementSystem
            ├─ StatusManager
            └─ Core 关卡结果规则组件（非独立系统）

关卡场景另由 `PlayerPresentationRoot` 等装配组件连接 Input、Placement、Camera、UI 和表现；这些不属于 `LevelContext` 持有模块。`PassageSystem` 文档保留为未接入设计，不列入当前运行时结构。
```

### 3.1 LevelContext 的职责

LevelContext 是当前关卡的依赖边界和生命周期容器。它负责创建、连接、暂停、恢复和销毁关卡级服务，但不替 Manager 或 Actor 保存第二份运行时数据。

LevelContext 至少持有：

- ConfigRegistry 的当前配置查询入口；
- Map 领域模块：
  - MapManager；
  - MechanismSystem；
- SlimeManager、EnemyManager、GuardManager；
- MovementSystem；
- StatusManager；
- Core 关卡结果规则组件（随 LevelContext 生命周期创建和销毁，不作为独立 Manager）；
- 当前关卡的 LevelEventBus；
- CampaignResourceLedger 的应用级战役资源引用（账本本身不归 LevelContext 所有）。

每个 Manager 都是独立系统文档中的公共模块，但不能脱离 LevelContext 成为跨关卡单例。Map 领域下辖的
`MapManager` 与 `MechanismSystem` 仍是两个独立的运行时边界：前者只拥有静态空间事实，后者拥有动态机关
实例和机关运行时数据；“属于地图领域”不等于 `MapManager` 可以直接创建、销毁或修改机关。

### 3.2 Actors 模块

Actors 模块包含个体和群体级自主决策生物：

- ActorCore：身份、阵营、生命和公共运行时数据；
- ActorDecisionTree：感知与行动意图；
- ActorStateMachine：行动执行、攻击时机、暂停和中断；
- SlimeActor、EnemyActor、GuardActor：具体个体行为；
- SlimeGroupActor：史莱姆群体行为，不拥有成员生命的第二份副本。

Manager 创建和驱动 Actor，Actor 自己拥有运行时数据。这个分离避免把“生成销毁”和“个体行为”混在同一个大型系统中。

## 4. 主要系统职责

### 4.1 核心与目标

GameRoot 负责应用级初始化和入口；LevelManager 负责场景加载、重开、暂停和关卡阶段；LevelContext 负责本局引用和 EventBus；Core 关卡结果规则组件只聚合已发生的结果事件并确认成功/失败。它不拥有武器、史莱姆或其他玩法运行时数据。

返回主菜单（2026-10-20）：设置、暂停和结算页经 UISystem 提交 ReturnToMainMenu，LevelManager 发布 ReturnToPreviousFlowRequestedEvent，GameRoot 选择 MainMenu 并调用 RequestUnloadToScene。LevelManager 停止旧局并释放 Context 后加载菜单，保留应用服务及战役账本；菜单不创建玩法 Context，重新选关创建新局。

`LevelManager` 订阅 `LevelResultRules.ResultDecided(LevelResult)` 并推进关卡阶段，再通过 `LevelResultReported` 通知表现层；当前代码没有 `LevelSucceededEvent` / `LevelFailedEvent` 事件类型。`GameRoot` 不接收当前关卡的玩法事件，也不保存关卡结果。

### 4.2 配置

ConfigSystem 提供 ScriptableObject 配置和校验。配置只描述设计时数据，不保存本局生命、状态、冷却、群体成员和目标。

架构预留 `TerrainConfig` 作为地形设计数据：描述 `TerrainId`、可通行性、连续移动修正以及进入/离开效果引用。具体字段和默认值在 ConfigSystem 设计冻结时确认；地形配置不保存某个关卡中某个格子的运行时状态。

### 4.3 四个 LevelContext Manager

| Manager | 负责 | 不负责 |
| --- | --- | --- |
| SlimeManager | SlimeActor、SlimeGroupActor 的生成、索引、驱动、销毁 | 不决定每只史莱姆的具体行为，不结算效果 |
| EnemyManager | EnemyActor 的生成、索引、驱动、销毁 | 不决定通用攻击规则，不直接扣血 |
| GuardManager | GuardActor 的生成、索引、驱动、销毁和指令入口 | 不解析原始输入，不直接改 Transform |
| MapManager | 场景地图绑定、道路/地形/区域/地图点查询、边界、静态阻挡识别和区域转移事实 | 不执行位移，不创建动态地图对象，不决定角色行动或结算效果 |
| MechanismSystem（Map 下辖子模块） | 食物、熔炉、障碍、已启用护送武器及其他已确认机关的运行时实例、生命周期、触发事实和公开快照 | 不替 MapManager 保存静态地图，不直接控制 Actor，不负责 Core 胜负规则 |

### 4.4 移动

MovementSystem 接收 ActorStateMachine、InputSystem 或其他合法调用方的移动请求，查询 MapManager 的空间事实和地形移速修正、查询 StatusManager 的 Actor 状态修正，然后执行位置变化、阻挡、碰撞和接触结果。MovementSystem 将刚体的实际位置同步给 MapManager；MapManager 据此发布区域进入/离开事实。

### 4.5 生命与状态

StatusManager 是效果和状态的唯一统一入口。Actor 持有自己的生命与状态数据，StatusManager 持有规则和计时，并通过 ActorCore 的效果接收契约修改目标。

StatusManager 负责 Actor 伤害、治疗、状态计时、易伤、控制、移速/攻速修正等效果，以及向 MovementSystem 提供 Actor 状态修正。首关不启用寒冷/炙热状态；熔炉不向 StatusManager 提交温度效果。守卫不消费食物、温暖或史莱姆状态修正。地形移速仍由 MovementSystem 从地图查询结果读取。击退待 MovementSystem 提供冲量接口后接入。StatusManager 不选择攻击目标，不处理攻击前摇和命中区域。

### 4.6 攻击行为

本架构不设置独立战斗系统。攻击是 Actor 的一种 Action：

```text
Perception
  → ActorDecisionTree
  → AttackIntent
  → ActorStateMachine / AttackAction
  → StatusManager.ApplyEffect
  → 目标 Actor 生命或状态变化
```

决策树负责“是否尝试攻击和攻击谁”；状态机负责攻击前摇、命中时机、后摇和打断；AttackAction 负责在命中时机做一次最终校验并提交 EffectRequest。攻击的生命变化不由决策树、动画或目标 Manager 直接完成。

治疗、自残、持续伤害和机关伤害可直接调用 StatusManager，不强行经过攻击流程。

### 4.7 机关、玩家和表现

MechanismSystem 是 Map 领域下辖的动态环境子模块，负责食物、熔炉、障碍、护送武器和 Castle 餐车等运行时实例、触发、库存请求、碰撞注册和生命周期。它不替代 `MapManager` 的静态空间查询，也不替代 Core 的胜负规则。宝箱、地刺和滚石目前由关卡场景适配器接线；陷阱参数资产尚未成为这些适配器的数据源。

PlacementSystem 使用 Grid 与 Anchor 吸附，最终放置条件由地图查询、格子占用、机关配置和后端共同复核；点击合法位置即提交。Anchor 安全替换经 `MechanismSystem.RequestPlaceAtAnchor` 事务处理，拆除经 `RequestRemove` 回收。战役库存由 `CampaignResourceLedger` 扣除且拆除不返还，重开本关恢复入场快照。PlacementSystem 不直接修改 Actor 状态。

InputSystem 使用新版 Unity Input System Package，把设备输入转换为语义指令；CameraSystem 负责视图；UISystem 和 PresentationSystem 消费状态与已发生事件。当前它们通过场景级装配接入，`PassageSystem` 尚未由 `LevelContext` 创建。

### 4.8 Core 结果规则与旧武器链路

Core 层由 `LevelContext` 创建轻量的 `LevelResultRules`，不创建旧 `ObjectiveSystem`。它只聚合当前关卡已经发生的事实并确认一次 `LevelResult`，再通知 `LevelManager` 推进生命周期。

当前 `LevelResultRules` 按 `LevelConfig.ObjectiveKind` 订阅事实事件。正式 `FirstLevel` 和 `Castle` 使用护送武器结果：武器抵达优先判胜，武器摧毁或 `SlimeDepletedEvent` 判负。洞穴模式统计当前存活洞穴人数，第一只进入后启动等待计时；达到阈值判胜、史莱姆耗尽立即判负、计时结束不足阈值判负。规则只读当前事件事实，不拥有 Actor 或武器对象。

当前配置差异：`ObjectiveConfig` 的字段未传入 `LevelResultRules`；洞穴阈值 6、等待 10 秒来自构造器默认值。Campaign 奖励使用精确关卡 ID，而配置的 Castle 奖励 ID 是 `SecondLevel`、关卡 ID 是 `Castle`。这些差异需要在配置/代码维护任务中修复，不在本次文档整理中代改。

## 5. 数据所有权

```text
ConfigSystem
  └─ 设计时配置，只读

Actor
  └─ 自身生命、状态、位置快照、目标和 AI 运行时数据

Manager
  └─ 同类型 Actor 的集合、索引、生命周期和聚合快照

StatusManager
  └─ 效果规则、状态计时、修正查询和效果结果

Map（地图领域）
  ├─ MapManager
  │    └─ 场景地图资源引用、静态地形/区域语义、空间事实和查询缓存
  └─ MechanismSystem
       └─ 食物、熔炉、障碍、护送武器兼容链路及其他机关运行时数据

MovementSystem
  └─ 移动请求、执行进度、碰撞和接触事实

MechanismSystem
  └─ 食物、熔炉、障碍及已确认机关运行时数据；护送武器若启用也只归此处

Core 关卡结果规则组件
  └─ 关卡结果阶段、原因和只读结果快照；不拥有武器或史莱姆数据
```

禁止两个系统各自维护同一生命、状态、位置或群体成员的可写副本。需要跨系统协作时使用公共查询、命令和结果事件。

## 6. 关键数据流

### 6.1 移动

```text
Input / ActorDecisionTree
  → ActorStateMachine
  → MovementSystem
  → StatusManager 查询移动修正
  → MapManager 查询空间事实
  → Actor 位置变化
  → MovementResult / MovementBlockedEvent
  → MapManager 比较区域成员关系并发布 MapAreaEntered/ExitedEvent
```

### 6.2 生命与状态

```text
Actor Action / 机关 / 环境 / 目标规则
  → EffectRequest
  → StatusManager
  → Target Actor 的生命或状态变化
  → EffectApplied / HealthChanged / ActorDied

地图区域进入/离开
  → MapManager 发布 MapAreaEntered/ExitedEvent
  → StatusManager 根据区域类型和配置申请或解除状态/效果
```

这里传递的是效果请求，不是把 Actor A 的生命值直接传给 Actor B。自残和治疗只是 TargetActorId 等于 A 的合法效果请求。

### 6.3 群体

```text
SlimeActor 的目标变化
  → SlimeManager
  → SlimeGroupActor 形成或更新
  → 群体上下文返回成员 Actor
  → 个体 DecisionTree / StateMachine
```

群体拥有关系和策略，不拥有成员生命、状态和碰撞体。

### 6.4 地形与环境

```text
场景 Tilemap / 地形语义数据
  → LevelSceneInstaller 或同类场景适配器绑定
  → MapManager 建立空间与地形查询
  → MovementSystem 查询目标位置的 TerrainId / 可通行性
  → 合并 TerrainConfig 的地形修正与 StatusManager 的角色修正
  → MovementResult / MovementBlockedEvent
  → 进入/离开地形事实
  → StatusManager 处理持续性状态或一次性效果
```

视觉 Tilemap 只负责显示；碰撞 Tilemap 或碰撞组件提供物理阻挡；地形语义数据提供 `TerrainId`、区域标签和效果引用。三者可以使用同一套关卡资源组织，但不能让视觉层直接承担玩法判定。动态食物、火炉和可移动障碍仍由 MechanismSystem 管理，并通过公开接口改变可查询的环境事实。

### 6.5 网格与 Anchor 放置

```text
InputSystem 屏幕位置事实
  → CameraSystem.ScreenToWorld
  → Unity Grid 的世界坐标/格子坐标转换
  → PlacementSystem 查询普通格子或策划 Anchor
  → PlacementGridView 显示当前放置状态
  → MechanismSystem 创建、替换或回收食物/熔炉/障碍
  → PlacementSystem.PlacementCompleted / MechanismSystem 结果事件
```

当前 Grid/Anchor 放置在最终确认时综合检查地图可占用条件、边界、机关占位与后端规则；不是所有地图边界内的空格都可放置。普通格子重复放置拒绝；Anchor 替换走 `MechanismSystem.RequestPlaceAtAnchor` 安全事务，拆除走 `RequestRemove`。动态 Actor 占用和多格机关等规则尚未由当前系统提供。武器、守卫和史莱姆不是玩家放置对象。

### 6.6 三路线与路线事实

```text
关卡场景路线与分支标记
  → MapManager 提供路线/Anchor 静态事实
  → 史莱姆感知适配器读取可通行分支与食物引导
  → SlimeActor 选择路线，MovementSystem 用 A* 执行 Actor 路径
  → 护送武器由 MechanismSystem 沿固定路线分段移动
  → LevelResultRules 按 LevelConfig.ObjectiveKind 结算结果
```

路线选择与空间路径搜索是不同职责：史莱姆在路线分支处按感知到的食物和可通行路线选定分支，之后 MovementSystem 用 A* 绕开局部阻挡。护送武器沿地图固定路线移动，当前阻挡时不会自动使用史莱姆的 A* 绕行。路线/Anchor 关联事实由 MapManager 提供，机关放置不直接改写 Actor 目标或位置。

### 6.7 场景装配与 SerializeField 协作边界

已确认采用“各自独立开发与测试 + 集成测试场景装配”的协作方式。暂定集成测试场景名为 `FirstLevelComposition_TEST`；它用于验证三位开发者的模块能否通过场景引用和公开接口组合，不等同于正式第一关场景，也不自动进入 Build Settings。

```text
小智：Map 领域（MapManager、MechanismSystem）、地图/路线/Anchor Authoring 与离线地图测试
  ┐
小宸：Camera/Grid/Placement/UI Prefab 与隔离测试
  ├─→ FirstLevelComposition_TEST
小茶：Actor Prefab、Spawner、Core 接线与组合层适配
  ┘          ↓
       SceneCompositionRoot / LevelSceneInstaller（候选装配组件）
                  ↓
       当前 LevelContext 的公开模块和快照
```

场景装配遵守以下边界：

- 场景可以通过 `[SerializeField] private` 保存 `GameObject`、`Transform`、具体 `MonoBehaviour`、Prefab 和 `ScriptableObject` 配置引用；不得为了 Inspector 可见而公开可写字段；
- `LevelContext`、`MapManager`、`MechanismSystem`、`StatusManager`、`LevelResultRules` 等由 `LevelContext` 创建的 plain C# 模块不直接作为场景字段序列化；场景装配组件在关卡启动后取得当前 Context，并通过公开接口完成绑定；
- Unity 默认不能把任意 plain C# 接口作为场景对象直接拖拽。需要序列化接口时，使用实现该接口的具体 `MonoBehaviour` 适配器或 `ScriptableObject` 配置，再由装配层转换为运行时接口；不能用反射或私有字段绕过所有权；
- 装配组件只负责引用校验、依赖注入、父节点/Prefab/Authoring 连接和生命周期转发，不拥有史莱姆、机关、地图、胜负规则的内部数据，也不复制一套 Manager；
- 装配组件应在 `Awake` 做本地引用和配置校验，在明确的 `LevelStarted`/安装阶段绑定当前 Context，在禁用、重开、失败、结算和场景卸载时取消订阅并清理自身临时对象；不能依赖多个脚本 `Start()` 的偶然顺序；
- 三位开发者交付的是可引用的 Authoring、Prefab、配置、适配器和独立测试，不是复制其他人的源代码。小茶可以负责集成测试场景的组合，但只能修改组合层和调用方，不能重写小智或小宸的系统内部规则；
- 独立测试夹具可以使用 Mock Backend、占位 Prefab 和模拟上游事实，但必须标记 `TEST_ONLY`，不能将模拟结果、调试对象或彩色方块作为正式机关/胜负闭环证据；
- 集成测试场景通过后，是否提升为正式 `FirstLevel` 场景、是否登记 Build Settings，仍需单独验收，不由场景组合自动决定。

推荐的集成测试场景根结构为：

```text
FirstLevelComposition_TEST
├─ MapRoot                 # 小智提供的 Bounds/Routes/Points/Anchors
├─ EntitiesRoot            # 小茶提供的 Slime/Enemy/Guard 运行时父节点
├─ MechanismsRoot          # 小智提供的机制 Prefab/Authoring
├─ PresentationRoot        # 小宸提供的 Camera/Input/Grid/Placement
├─ UIRoot                  # 小宸提供的 HUD/Selection
└─ SystemsRoot             # 组合层 Installer/Spawner 适配
```

场景数据流保持为：

```text
SerializeField 的场景引用
  → 装配组件校验并连接当前 LevelContext
  → MapManager 建立地图快照 / Manager 创建运行时对象
  → Placement/UI/Actor 通过公开接口提交命令或读取快照
  → LevelEventBus 发布已发生事实
  → 集成测试验证暂停、重开、失败、结算和卸载清理
```

该机制降低场景资源合并的耦合，但不替代路线、Anchor、机关创建、终点结果和 Tick 顺序等公共契约的确认。

## 7. 通信规则

- 能明确找到办理者的同步规则使用公开方法调用；
- 需要多个观察者得知的已发生结果使用当前 LevelContext 的 LevelEventBus；
- EventBus 不用于替代命令，不承载可写对象，不跨关卡存在；
- UI、表现和调试工具只能查询快照或提交公开命令；
- 不能通过读取其他系统私有字段完成协作。

## 8. 关卡生命周期

```text
未加载
  → 加载中
  → 初始化
  → 运行中 ⇄ 暂停
  → 结算中
  → 重开或离开
  → 清理
```

初始化顺序：

1. 加载场景和关卡配置；
2. 创建 LevelContext 与 LevelEventBus；
3. 创建并绑定 MapManager；
4. 由 LevelSceneInstaller 或同类场景适配器把视觉 Tilemap、碰撞数据、地形语义和出生点绑定到 MapManager；
5. 创建 SlimeManager、EnemyManager、GuardManager、MovementSystem、StatusManager 和 MechanismSystem；
6. 创建 Core 关卡结果规则组件、输入、镜头、UI、表现及已确认的机关适配；
7. 通过 Manager 生成初始 Actor；
8. UI 主动读取初始快照；
9. 发布 LevelStartedEvent。

暂停时停止 Actor AI、移动、效果计时、群体计时和机关冷却；UI 和必要的暂停输入仍然可用。重开采用重新加载当前场景，旧 LevelContext、Manager、Actor、状态和订阅必须先失效。

## 10. 小宸 P0 接入记录（2026-10-09）

InputSystem、CameraSystem、UISystem 的首版由场景级 `SlimeBattle.Player.PlayerPresentationRoot` 显式组装，不修改现有 Core 的创建与状态实现。只在场景入口查找一次 Bootstrap 持久化的 LevelManager；日常通过公开方法和其 C# 事件连接。输入在 Running 为 Gameplay，暂停/结算为 UiOnly，其余阶段禁用。
