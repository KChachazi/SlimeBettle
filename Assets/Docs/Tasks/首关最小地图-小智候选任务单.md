# 首关最小地图任务单：小智（Map + Mechanism）

状态：已确认分工（2026-10-15）
依据：用户提供的最新《第一关.docx》、`项目架构.md` 0.8、`16-MapManager.md`、`19-MechanismSystem.md`、`17-MovementSystem.md`
目标：完成首关 Map 领域，包括地图事实、三路线、Anchor 查询、移动执行和全部当前机关运行时；不负责 Actors/AI、Player/UI 或 Core 结果规则内部逻辑

## 1. 任务目标

为明天策划提供的第一关草图建立可被程序测试的地图事实：

- 正式记录地形、地图边界、出生点、敌人点、终点洞穴、三路线和 L/SL Anchor；护送武器点仅作为兼容链路可选点位；
- 提供可查询的三条预绘制路线事实，按稳定顺序包含终点、分支/主线和关联阻断/陷阱点；
- 使用现有 `MovementSystem` 执行普通 Actor 的直线移动，并为兼容护送武器提供经接口评审后确认的路线分段移动适配；
- 保留静态碰撞和地形移动修正边界；
- 首关不实现动态网格寻路，不把固定路线误称为通用寻路；
- 为 Grid + Snap Anchor 放置提供地图边界、Anchor 位置和只读配置事实，但不实现 `PlacementSystem` 的预览、占用或替换规则。

### 1.1 Map 下辖 MechanismSystem（必须完成）

- 维护食物、熔炉、障碍和现有 `EscortWeapon` 兼容链路的运行时所有权、实例生命周期、公开快照和事件；后续纳入首关的陷阱、补给等机关也由本模块按确认后的接口接入；
- 由 `MechanismSystem` 完成机关创建、替换、回收、触发、动态阻挡注册和 `LevelContext` 生命周期清理；场景组合层、PlacementSystem 和 UI 不得直接 `Instantiate`、`Destroy` 或修改机关内部状态；
- 熔炉首关只作为引导源，不向 `StatusManager` 申请寒冷/炙热状态；护送武器链路作为兼容/后续扩展，不覆盖最新第一关史莱姆终点胜利条件；
- 为小宸提供稳定的公开放置/替换/快照接口，为小茶提供机关事实、武器兼容事件和只读查询；公共接口变化必须先更新 `99-全局API查询表.md` 并通知调用方；
- 机关内部规则、测试和 Prefab 可在本任务中维护，但不得把 MapManager 的静态空间查询、Actor 行为或 Core 结果判定复制进机关系统。

首关不配置寒冷/炙热玩法效果；地形属于首关范围，但具体地形类型、倍率和进入/离开效果仍以系统设计文档和策划草图为准。

## 2. 前置依赖

1. 等待策划草图，确认三条路线点、终点洞穴、L/SL Anchor、地形区域和静态障碍的几何位置；
2. 使用已确认的 `MapManager` 空间查询和 `MovementSystem` 移动接口；
3. 向小茶提供只读 `MapRouteSnapshot`、Anchor 事实和运输/阻挡事实，不暴露可写场景组件；
4. 向小宸提供地图边界、世界坐标和 Anchor 语义，避免 UI/放置层自行推导边界。

路线被玩家障碍占用后的选择时机和同帧优先级尚未确认。本任务只能发布路线/阻挡/关联 Anchor 事实，不能私自选择“自动绕行”“忽略障碍”或“阻挡即失败”。

## 5. 公开接口边界

可以维护或实现以下地图/移动边界，但新增签名必须先登记到 `99-全局API查询表.md`：

- `MapManager.TryGetMapBounds(...)`；
- `MapManager.Query(...)`、`TryGetMapPoint(...)`；
- `MapManager.TryGetRoute(MapRouteId, out MapRouteSnapshot)`；
- 候选的 `MapManager.TryGetPlacementAnchor(PlacementAnchorId, out PlacementAnchorSnapshot)`；最终签名、payload 和类型名待评审；
- `MapManager.GetMovementSpeedMultiplier(...)`、静态阻挡查询；
- `MovementSystem.SubmitMovement(...)`、取消、移动状态和接触结果；
- 非 Actor 护送武器的运输移动适配（签名待确认）；
- `MovementBlockedEvent`。

`MapManager` 不得创建或销毁史莱姆、守卫、敌人、武器、机关、陷阱或结果组件；机关创建和生命周期只能由本任务负责的 `MechanismSystem` 执行；不得通过读取其他系统私有字段判断路线运输状态。

1. 首关地图边界、地形、出生点、终点洞穴、敌人点、三路线和 L/SL Anchor 的 authoring/查询方案；
2. 三条路线的稳定 ID、有序路点、分支/主线和关联阻断/陷阱点表达；
3. 地形移动修正接入 MovementSystem 的最小验证；
4. 静态碰撞和越界查询的 EditMode/PlayMode 测试；
5. 三路线/Anchor 查询、关联关系和兼容分段移动的测试夹具；
6. 一份面向场景作者的草图标注约定：视觉地形、静态碰撞、路线节点、Anchor 和可放置区域分别如何表达；
7. 食物/熔炉/障碍/护送武器兼容链路的机关运行时、Prefab/Authoring 和公开接口测试；
8. PR 描述中的验证层级：编译、EditMode、PlayMode、人工运行和未验证项必须分开写。

### 6.1 场景装配交付形式

- 地图内容以 `MapBoundsAuthoring`、`MapRouteAuthoring`、`MapPointAuthoring`、地形/区域 Authoring 和经确认的 Anchor Authoring 交付；不把地图运行时 Manager 复制到测试场景中；
- 提供一个可被集成场景通过 `SerializeField` 引用的地图 Authoring/Prefab 组合或独立地图测试夹具，暂定集成场景为 `FirstLevelComposition_TEST`；
- 地图 Authoring 只提供边界、路线、点位、区域和 Anchor 的事实，运行时由 `MapManager` 建立快照；不让 UI、Placement 或 Actor 直接保存第二份路线数据；
- 如果 Anchor 的最终公共查询接口尚未确认，可以先交付 Authoring 和隔离查询测试，但必须把接口标记为候选，不以临时字段名要求其他模块接入；
- 小智不负责修改共享集成场景的其他模块对象；需要验证组合时，向小茶提供引用说明、对象层级和字段配置表。

## 7. 验收标准

- 同一关卡中边界、路线 ID、路点 ID 和地图点 ID 可诊断且稳定；
- `MapManager` 能返回三条路线的有序路点、终点和关联事实，路线查询不执行动态寻路；
- 普通 Actor 仍由 MovementSystem 直线移动，静态阻挡产生 `MovementBlockedEvent`；
- 地形移动倍率通过 MapManager → MovementSystem 生效，不修改 Actor 基础配置；
- Grid + Snap Anchor 放置可获得地图边界和 Anchor 只读事实，但 MapManager 不直接创建、回收或替换放置对象；
- 食物、熔炉、障碍和兼容护送武器均由 `MechanismSystem` 统一创建/维护/清理，机关事件由其发布；熔炉不产生冷热状态；
- 暂停、重开和 Dispose 后不会保留旧地图索引、区域成员和路线引用；
- 不修改正式场景、Build Settings、Actors/Player/UI/Core 内部实现。

## 8. 并行和合并顺序

- 与小茶：先完成 Map/Mechanism 快照、事件和移动事实契约，再由小茶并行开发 Actors/AI 与结果接线；
- 与小宸：先提供边界、坐标、Anchor 和机关放置请求契约，小宸在自己的测试场景中验证 Grid + Anchor 映射；
- 合并建议：Map/Mechanism 查询、运行时和测试 → Placement/Grid 适配 → Actors/AI 与 Core 接线 → 首关场景装配；
- 地图 PR 不应把正式关卡草图直接写入 `Level_test`，除非另行确认场景整合任务。
- 小智的 Map/Mechanism 可以先在独立测试场景中完成；共享集成场景由指定集成者统一拼装，避免多人同时编辑同一个 `.unity` 文件。

## 9. 必须回报的问题

- 草图中的哪些区域是纯视觉地形、静态碰撞、可通行路线或不可通行区域；
- 固定路线是否允许经过会被玩家放置障碍的格子；
- 地形倍率和边界坐标单位；
- 路线被阻挡后由谁决定后续选择、等待或失败；Anchor 关联事实是否需要独立事件。
