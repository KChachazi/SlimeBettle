# 首关最小地图候选任务单：小茶

状态：候选分工，待用户确认后生效
依据：`Assets/Docs/SlimeBettle设计文档-3.docx`、`项目架构.md` 0.5、相关系统文档和 `99-全局API查询表.md`
目标：完成首关 Actors / Mechanism 运行时闭环，不负责地图、放置表现或 Core 结果规则的最终实现

## 1. 任务目标

为第一张程序测试地图准备以下运行时能力：

- 史莱姆上限按最新确认限制为 20；
- 史莱姆、敌人、守卫可以由当前 `LevelContext` 创建、驱动和销毁；
- 守卫围绕护送武器防守；守卫不受食物、熔炉引导、温暖或史莱姆状态影响；
- 食物、熔炉、障碍作为 `MechanismSystem` 管理的三种首关机关；
- 护送武器作为 `MechanismKind.EscortWeapon`，由 `MechanismSystem` 完全拥有生命、运输状态、固定路线进度和终点状态；
- `MechanismSystem` 发布武器受击、摧毁和抵达终点事实；`SlimeManager` 在最后一只史莱姆死亡后发布 `SlimeDepletedEvent`；
- 熔炉首关只提供引导源，不向 `StatusManager` 申请寒冷/炙热状态。

状态优先级、复杂群体策略、武器最终伤害入口和路线被障碍占用后的规则不在本任务中自行决定。

## 2. 前置依赖

1. 先确认本轮 Event 类型、命名空间和只读 payload 的公共契约；
2. 依赖小智提供的 `MapManager` 固定路线只读查询和经确认的机制运输移动适配；不得直接把 Actor 专用移动请求套用到武器；
3. 依赖小宸使用 `PlacementSystem` 提交已通过网格边界/占用校验的机关确认；
4. Core 结果规则组件只消费事件，不应要求本任务直接调用或修改其内部状态。

如果 `Weapon` 伤害请求、固定路线数据格式或守卫数量尚未确认，先提交接口问题，不在 PR 中用临时公共 API 固化。

## 3. 允许修改的目录

- `Assets/Game/Scripts/Actors/`
- `Assets/Game/Scripts/Mechanism/`
- 与上述运行时类型直接对应的 `Assets/Game/Scripts/Data/Config/`
- `Assets/Game/Tests/` 下独立的 EditMode / PlayMode 测试夹具和测试场景

## 4. 不允许修改的目录或资产

- `Assets/Game/Scripts/World/`：地图、路线和移动由小智候选任务负责；
- `Assets/Game/Scripts/Player/`、`Assets/Game/Scripts/UI/`：输入、网格预览和 UI 由小宸候选任务负责；
- `Assets/Game/Scripts/Core/`：结果规则组件和生命周期协调需由总计划先确认；
- `Assets/Game/Scenes/Level_test.unity`、Bootstrap、MainMenu 和其他正式场景；
- `ProjectSettings/EditorBuildSettings.asset`；
- `Assets/Game/Scripts/Objectives/`：不得在旧目录继续新增武器运行时逻辑或扩展旧 `ObjectiveSystem`。

## 5. 公开接口边界

只能使用已登记或经提前确认的公开接口：

- `LevelContext` / `LevelEventBus` 的当前关卡生命周期；
- `MapManager.TryGetRoute(...)`、地图点和空间查询；
- 经确认的机制运输移动适配、取消和移动结果；普通 Actor 才使用 `MovementSystem.SubmitMovement(...)`；
- `StatusManager` 的 Actor 效果接口；守卫不得申请食物、温暖或史莱姆状态；
- `PlacementSystem` 提交的机关放置结果；
- 向 EventBus 发布 `WeaponDamagedEvent`、`WeaponDestroyedEvent`、`WeaponReachedGoalEvent`、`SlimeDepletedEvent`。

不得读取其他系统的私有字段，不得让预制体直接调用 Actor 内部方法，不得让 UI 或动画回调改变武器生命或判定胜负。

## 6. 交付物

1. `MechanismSystem` 的首关机关运行时边界和只读快照；
2. `EscortWeapon` 的运行时数据、固定路线分段推进和目标点事实；
3. `WeaponDamagedEvent`、`WeaponDestroyedEvent`、`WeaponReachedGoalEvent` 的发布实现；
4. `GuardManager` / `GuardActor` 的首关生成与护送武器关联；
5. `SlimeManager` 的 20 只上限验证和 `SlimeDepletedEvent`；
6. 对应 EditMode 测试；必要时提供不修改正式场景的 PlayMode 测试夹具；
7. PR 描述中的文件清单、接口依赖、静态检查结果、EditMode/PlayMode 结果和未验证项。

## 7. 验收标准

- 史莱姆超过 20 只的生成请求被拒绝，且已有史莱姆不受影响；
- 最后一只史莱姆确认死亡时只发布一次 `SlimeDepletedEvent`；
- 武器生命只能由 `MechanismSystem` 修改，归零只发布一次 `WeaponDestroyedEvent`；
- 武器按固定路线点推进，到达终点只发布一次 `WeaponReachedGoalEvent`；动态寻路不作为本 PR 验收项；
- 熔炉可被感知为引导源，但首关不会添加寒冷/炙热状态；
- 守卫可读取武器快照并执行防守，食物/熔炉/史莱姆状态不会改变守卫的行为修正；
- `Dispose`、暂停、失败和重开后旧武器、守卫、事件订阅和计时器全部失效；
- 没有修改正式场景、Build Settings 或其他系统内部实现。

## 8. 并行和合并顺序

- 与小智：在事件和路线查询契约确认后并行；小茶不改小智的地图内部实现；
- 与小宸：机关快照和放置确认接口确认后并行；小茶不改小宸的 GridView / UI 内部实现；
- 合并建议：公共事件/快照契约 → 小智地图/路线 → 小茶 Mechanism/Actors → 小宸放置/UI 适配 → 独立场景联调；
- 本任务 PR 必须邀请至少一名其他开发者审核；没有运行时证据时只能标记为“静态/测试夹具通过”。

## 9. 必须回报的问题

- 守卫数量和初始生成点；
- 武器伤害入口的最终公开签名；
- 运输所需史莱姆数量和缺少载体时的速度规则；
- 固定路线被障碍占用时是等待、失败、禁止该次放置还是其他规则；
- 成功与失败事件同一更新周期同时到达时的优先级。
