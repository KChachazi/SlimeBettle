## 0. 当前审查结论与任务边界

当前 `xcha` 分支是与最新 `master` 合并后的工作基线，并包含未提交的场景、Player/UI 和测试改动；首关闭环仍未形成。以下是本任务必须正视的仓库事实：

- `MechanismSystem` 已存在 `EscortWeapon`、武器快照和武器事实事件；`GuardManager` / `GuardActor` 也已存在。它们是当前代码事实，不等于已经符合最新第一关的结果口径；
- `LevelResultRules` 当前仍监听武器抵达、武器摧毁和史莱姆耗尽事件，第一关最新策划要求的“至少 6 只史莱姆进入终点洞穴 + 等待窗口”尚未接入；
- `MechanismPlacementBackend` 已能把食物、熔炉、障碍放置请求交给 `MechanismSystem`，但当前尚未实现 Grid + Snap Anchor、L/SL 替换事务和路线/陷阱联动；测试中的彩色方块不能作为正式机关创建证据；
- 当前测试仍能看到旧的史莱姆上限/旧结果口径用例，必须在不掩盖旧兼容行为的前提下区分“历史测试通过”和“最新第一关验收通过”；
- 熔炉“仅引导、不产生冷热”、守卫排除食物/温暖/史莱姆状态的规则需要独立运行验证，不能只看配置或文档；
- 正式 `Level_test` 尚未装配最新策划要求的三路线、终点洞穴统计、L/SL Anchor、地形和陷阱/补给；本任务不擅自修改正式场景；
- 仓库中存在已提交的 `Assets/Game/Tests/TestScene.unity.meta` 冲突标记。该问题属于合并卫生阻塞，不得在本任务中静默选择一方覆盖。

因此，本任务以小茶个人 Actors / Mechanism 模块为主线，负责受控接入最新第一关的终点统计、三路线事实、Grid + Snap Anchor 放置和必要的跨模块适配；不把旧武器链路或测试夹具自动提升为最新第一关规则。

## 1. 已确认的首关目标

最新第一关闭环包含：史莱姆、敌人、守卫、地形、终点洞穴、三条预绘制路线，以及食物、熔炉、障碍、陷阱和补给等策划元素。

- 史莱姆上限为 20；
- 成功条件为至少 6 只史莱姆进入终点洞穴；等待窗口结束时仍不足 6 只则失败；
- 守卫不受食物、温暖或史莱姆状态效果影响；
- 第一周目不实现寒冷/炙热效果，熔炉仅作为引导源；
- 三条路线按场景配置的路线事实实现，不等同于通用动态寻路；L1/L2/L3 与 SL1/SL2/SL3 的具体关联来自 Anchor 配置；
- 放置使用“Unity Grid + Snap Anchor + 独立放置可视化”；普通格子边界内默认合法且单格唯一，重复放置拒绝；Anchor 只接受配置允许的类型；
- 当前第一关 L/SL Anchor 的障碍允许替换旧障碍，必须先通过 `MechanismSystem` 回收旧对象，再提交新对象；替换失败不得丢失旧对象；
- 旧护送武器链路由 `MechanismSystem` 拥有并可继续作为兼容/后续扩展，但在最新第一关策划重新确认前不作为本关胜利条件；
- 状态行为优先级、三路线选择时机、路线同帧阻断优先级、陷阱/补给的最终运行时归属仍待确认，不得在本任务中自行定案。

## 2. 小茶个人模块（必须完成）

### 2.1 Mechanism 运行时

- 保持食物、熔炉、障碍和现有 `EscortWeapon` 的运行时所有权边界；旧武器事件链路不得扩展为最新第一关的成功条件；
- 为障碍接入普通 Grid 与 L/SL Anchor 的放置/替换事务：普通格子重复放置拒绝，允许替换的 Anchor 先回收旧障碍，再创建新障碍，失败时保留旧对象；
- 熔炉可以被史莱姆感知为引导源，但首关路径不得申请或施加寒冷/炙热状态；不得破坏以后接入冷热系统的扩展点；
- 为第一关陷阱/补给和局部食物供给预留明确适配边界；如果最终所有者未确认，只完成事实转换和阻塞报告，不在 MechanismSystem 中擅自新增完整子系统；
- 保持现有武器快照和武器事实事件的生命周期正确性，供兼容关卡/后续扩展读取；
- 机关创建、销毁、暂停、失败、重开和场景切换必须遵循 `LevelContext` 生命周期；不得把运行时机关留在静态全局单例中。

### 2.2 Actors 运行时

- 在现有 `GuardManager` / `GuardActor` 基础上完成第一关场景接入、生命周期和基础防守行为验证；不要重复创建平行 Guard 实现；
- 守卫只能通过公开快照/事件读取武器和敌人事实，不得直接访问其他系统私有字段；
- 守卫不参与食物、熔炉、温暖或史莱姆状态效果；相关免疫必须有可测试的运行时路径，而不是只保留配置值；
- 将史莱姆上限落实到首关配置和运行时校验；超过 20 的创建请求必须被拒绝；
- 在最后一只史莱姆确认死亡时发布一次 `SlimeDepletedEvent`，并覆盖重开后事件状态重置；
- 增加或适配“史莱姆进入终点洞穴”的只读统计事实，供 Core 结果规则累计达到 6 只；终点统计不直接判定胜负；
- 保持三条路线是关卡事实/目标候选，不在 Actor 侧写死路线选择优先级；
- 状态行为优先级暂按系统设计文档执行。遇到文档未覆盖的优先级，不得用代码顺手固化，应在 PR 中列为待确认问题。

### 2.3 测试

- 为现有武器兼容链路、Anchor 替换事务、史莱姆上限、史莱姆终点统计、史莱姆耗尽、守卫免疫和生命周期清理补充 EditMode 测试；
- 为三路线事实查询、L/SL 关联和普通格子重复放置补充不依赖正式场景的适配测试；
- 需要跨模块验证时，只能新增 `Assets/Game/Tests/` 下的独立测试夹具或测试场景；不得把测试对象、彩色方块、模拟结果调用带入正式场景；
- 测试直接调用 `LevelManager.ReportResult(...)`、旧武器结果事件或 TEST_ONLY 放置后端，只能证明测试夹具/兼容链路接线，不能作为最新第一关 Core 自动判定或正式机关创建通过的证据；
- PR 必须区分静态检查、编译检查、EditMode、PlayMode、人工运行和真机验证；没有实际证据的项目标记为“未验证”。

## 3. 跨模块适配职责（必须完成，但受边界约束）

小茶可以修改另两位开发者的代码模块，但只允许修改“接入点、适配器、调用方和测试夹具”，不得重写对方负责的系统内部规则。每一项跨模块修改都必须在 PR 描述中列出文件、原因和接口影响。

### 3.1 适配小智的 Map / 路线模块

允许：

- 通过 `MapManager.TryGetRoute(...)` 和已确认的路线只读接口读取三条路线、起点、路点、终点及 L/SL 关联事实；
- 在 Actors/关卡规则侧增加路线候选适配，使史莱姆消费路线事实而不是把路线选择硬编码到 MapManager；
- 为路线/Anchor 接口转换补充查询测试、关联关系测试和阻断事实观测；
- 保留现有武器运输适配作为兼容路径，但不得把它改写成最新第一关的胜利判定。

不允许：

- 修改 `MapManager` 的区域、边界、路线数据模型或寻路算法来掩盖 Anchor/路线接入问题；
- 自行决定路线被障碍占用时等待、失败、禁止放置、自动改道或同帧优先级；

### 3.2 适配小宸的 Placement / Player / UI 模块

允许：

- 将当前 placement backend 适配为调用 `MechanismSystem` 的公开创建/替换请求；

- 将玩家确认放置的结果接到 Mechanism 快照/事件，并让 UI 读取真实的武器、史莱姆和结果状态；
- 修改 `FirstLevelPresentationRoot`、placement backend 或 status source 的调用方，以适配实际运行时对象。

不允许：

- 由 Player、UI 或 PlacementSystem 直接 `Instantiate`、修改机关生命、推进武器路线或判定胜负；
- 改变“普通格边界内合法、单格唯一，Anchor 按配置替换”的首关放置规则；
- 修改 Input Action Map、点击语义、网格原点/尺寸等尚未确认的公共契约；如接入确实需要变化，先报告接口问题；
- 把测试彩色方块或 TEST_ONLY backend 当成正式机关实现。

### 3.3 Core 结果接线

本任务可以为 Core 结果规则提供事件适配和快照接线，但不得自行决定结果规则的优先级、命名或迁移策略：

- 旧 `ObjectiveSystem` 不得继续扩展武器运行时逻辑；
- 最新第一关结果规则应消费史莱姆终点进入统计、等待窗口结束和耗尽事实；旧武器事件只作为兼容链路；
- `LevelManager` 只负责接收最终结果并控制关卡生命周期；
- 如果接线需要新增或改变 Core 公共 API，先提交接口说明，待总计划确认后再实现；
- 在 Core 结果组件尚未确认前，不得用 `LevelManager.ReportResult(...)`、旧武器事件或测试 backend 伪造最新第一关成功/失败闭环。

### 3.4 集成测试场景装配职责

在三位同学各自的模块和隔离测试完成后，小茶负责维护首关集成测试场景（暂定名 `FirstLevelComposition_TEST`），将大家交付的场景 Authoring、Prefab、配置和适配器通过 Inspector 引用拼装到一起。

小茶的组合职责包括：

- 在 `SystemsRoot` 放置受限的 `SceneCompositionRoot`/`LevelSceneInstaller`（名称仍可调整），通过 `[SerializeField] private` 绑定 `MapRoot`、`EntitiesRoot`、`MechanismsRoot`、`PresentationRoot`、`UIRoot`、Prefab、出生点和配置；
- 在 `LevelStarted` 或明确的安装阶段取得当前 `LevelContext`，将场景事实和父节点交给既有 Manager/Adapter；不在 Installer 中创建第二套 `LevelContext`、Manager、Actor 列表或胜负规则；

## 7. 验收标准

- 史莱姆超过 20 只的生成请求被拒绝，且已有史莱姆不受影响；
- 最后一只史莱姆确认死亡时只发布一次 `SlimeDepletedEvent`，重开后可再次正确发布；
- 史莱姆进入终点洞穴的事实可累计，达到 6 只；等待窗口结束时不足 6 只才进入失败事实；结果组件只确认一次；
- 普通 Grid 同格重复放置被拒绝；L/SL Anchor 只接受配置允许的机关；障碍替换先回收旧对象，失败时旧对象仍有效；
- 通过小宸的放置入口创建真实的 MechanismSystem 机关；Player/UI 不直接创建或修改机关内部状态；
- 食物、熔炉、障碍三种机关可被首关适配层识别；熔炉只提供引导，不添加寒冷/炙热状态；
- 守卫可读取公开快照/事件并执行基础防守；食物/熔炉/史莱姆状态不会改变守卫行为修正；
- 三路线和 L/SL 关联事实可查询，路线选择不由 MapManager 私自执行动态寻路；
- 旧武器链路的生命和事件仍只由 MechanismSystem 修改，但不能伪造最新第一关成功；
- Core 结果规则只消费事实事件；不能以手动 `ReportResult`、旧武器事件或测试 backend 作为最新第一关闭环证据；
- `Dispose`、暂停、失败、重开和场景切换后旧机关、守卫、事件订阅和计时器全部失效；
- 没有修改正式场景、Build Settings 或已提交冲突文件；
- 所有验证结论标注证据类型，没有把编译或测试夹具结果写成“玩家运行通过”。

### 阶段 C：跨模块适配

- 接入小智的三路线/Anchor 只读查询；
- 接入小宸的 Grid + Anchor 放置确认、替换事务和真实机关创建；
- 接入 UI 的真实快照/事件来源；
- 仅修改适配器和调用方，发现需要改变对方内部规则时暂停并回报。

### 阶段 D：独立联调夹具

- 在 `Assets/Game/Tests/` 创建不污染正式场景的最小集成夹具；
- 验证放置食物、熔炉、障碍，普通格/Anchor 重复与替换，生成史莱姆/守卫，三路线事实和终点统计；兼容武器运输单独记录，不替代第一关结果验证；
- 策划草图到位后，再由总计划安排正式场景装配和 Build Settings 核对。

推荐合并顺序：公共事件/快照/路线契约确认 → 小茶个人 Mechanism/Actors → 小茶跨模块适配 → 独立联调夹具 → 正式场景装配。每个 PR 至少邀请一名其他开发者审核；未有运行时证据的部分必须标记为“未验证”。

集成测试场景的实际合并顺序为：小智地图 Authoring/路线事实 → 小宸 Camera/Grid/Placement/UI 组合 → 小茶 Actor/Mechanism 与组合层 Installer → Core 结果/终点统计接线 → 场景运行验证。任何一步需要改变未确认的公共契约，都必须先停在接口报告，不得用 Inspector 引用掩盖契约缺口。

## 9. 必须回报的问题

- 守卫数量、初始生成点和守卫的攻击/防守行为边界；
- 史莱姆进入终点洞穴的检测方式、等待窗口事件和同帧结果优先级；
- 三路线选择时机、L1/L2/L3 的阻断语义、SL1/SL2/SL3 的陷阱关联和同帧优先级；
- Anchor 替换失败时的事务回滚/旧对象保留语义；
- 陷阱、补给和局部食物供给的最终运行时所有者、触发接口和资源规则；
- 兼容武器链路是否重新进入某一关、运输所需史莱姆数量、路线推进和伤害入口的最终参数；
- Core 结果规则组件的最终名称、归属文件和 `LevelManager` 接收接口；
- 小宸 placement backend 的正式创建请求签名和 MechanismConfig 的 prefab/装配来源；
- 小智路线/Anchor 数据在正式草图中的节点命名、终点洞穴、碰撞/阻塞标记和路线关联。
