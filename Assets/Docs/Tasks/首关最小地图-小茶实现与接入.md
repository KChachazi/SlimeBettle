# 首关最小地图：小茶实现与接入

日期：2026-10-17。依据《第一关.docx》、小茶任务单，以及本轮确认的洞穴人数、岔路选择、Anchor 替换和机关上限规则。

## 交付与入口

- 正式场景：`Assets/Game/Scenes/FirstLevel.unity`，已登记在 `ProjectSettings/EditorBuildSettings.asset`，顺序为 `Bootstrap → MainMenu → FirstLevel → Level_test`。主菜单的开始按钮和关卡选择按钮都调用 `StartFirstLevel()`，由持久化 `GameRoot/LevelManager` 加载正式首关。
- 正式场景由 `FirstLevelCompositionRoot` 绑定正式 `PF_FirstLevelMapData`、`EntitiesRoot`、`MechanismsRoot`、`PF_FirstLevelPlayer` 和 Actor 配置；场景内不再放置重复的 `LevelManager`，而是在持久化 Manager 发布 `LevelStarted` 后完成组合。这样正式场景可由启动流程加载，也可继续复用同一套组合接口。
- 回归夹具：`Assets/Game/Tests/FirstLevelComposition/FirstLevelComposition_TEST.unity` 保留本地 `LevelManager` 和测试配置，用于隔离组合回归；它不代表正式关卡入口。测试夹具和正式场景都使用正式 Actor/Mechanism/UI 代码，不包含临时彩色方块或模拟胜负。
- 启动顺序：Bootstrap 中的持久化 `GameRoot/LevelManager` 初始化配置注册表，BootstrapMenuLoader 加载 MainMenu；开始按钮请求 `FirstLevel`，LevelManager 加载正式场景并构造 `LevelContext`；发布 `LevelStarted` 后组合根接入路线感知与 Actor 行动端口、设置生成父节点，并在地图 Spawn 位置生成 1 只史莱姆及两个自由史莱姆，在 EnemySpawn 位置生成敌人。`LevelContext` 根据 GuardSpawn 创建守卫。玩家组件在 `LevelStarted` 时重建放置与 UI 会话。
- 可在场景 HUD 选择食物、熔炉、障碍，并在地图上确认放置。食物由正式 `MechanismSystem` 创建，史莱姆接触食物触发正式状态/机关事件，`LevelContext` 增殖一只史莱姆；最多存活 20 只。熔炉只作引导源，不在此关引入冷热效果。障碍放在 L Anchor 会阻断后续岔路选择，放在已占用 Anchor 上走专用替换事务。

## 运行规则

- 自由史莱姆默认在各自出生位置半径 1.5 个世界单位内等待，不自动跑向岔路。感知范围内出现新食物时可直接前往；障碍状态解除，或组合根调用 `ReleaseSlimeRoutes()` 后，史莱姆才抵达岔路并选路一次。有多个可用食物时随机选一个引导；没有食物指向开放路线时走路线 2，路线 2 被封时按 1、3 选开放路线。三路全封则在岔路等待；已选路的史莱姆不因后续封路改道。分支与主线路点来自地图快照。
- 史莱姆行为优先级为害怕、对应需求引导、最近战斗目标、普通引导。害怕时忽略食物/熔炉；饥饿优先食物，寒冷优先温暖/熔炉；没有更高优先级目标时，暴躁及正常史莱姆在感知范围内选择最近的食物或熔炉。熔炉到达后保持可用的持续引导，不因一次到达被路线感知标记为已访问。
- 洞穴人数是当前仍在洞穴内且存活的史莱姆数。首只进入时启动 10 秒等待；人数达到 6 则成功，等待结束仍不足 6 则失败，最后一只存活史莱姆死亡时立即失败。`LevelResultRules` 在帧末只确认一次结果；旧武器事件不决定本关胜负。
- 首关守卫站岗点按策划修正为设计坐标 `(691,806)`，索敌 300px、攻击范围 260px、站岗半径 800px；守卫不作为史莱姆状态目标。食物、温暖或史莱姆状态不会作用于守卫。
- 首关敌人无目标时以各自出生点为中心在局部活动矩形内巡游，默认半边长 4 个世界单位并裁剪到地图边界；守卫读取护送武器实时位置，按 `EscortDistance` 跟随并在 `LeashDistance` 内防守，不再把固定出生点作为唯一护送站位。
- 玩家放置机关总数上限为 20，其中障碍最多同时存在 10 个，移除后返还可用名额。Anchor 替换由 `MechanismSystem.RequestPlaceAtAnchor(configId, anchorId)` 预检并注册新机关，成功后才回收旧机关；失败时旧机关保留。Player 只发送请求，预览可显示“可替换”。

## 跨模块接口与修改原因

| 位置 | 修改与原因 |
| --- | --- |
| `Actors/` | 史莱姆洞穴占用/耗尽事实、三路线感知、守卫站岗行为、组合根；使地图事实由现有 Actor 运行时消费。 |
| `Core/LevelContext.cs`、`LevelResultRules.cs`、`LevelManager.cs` | 接通洞穴结果、食物增殖、守卫出生和当前场景启动/原地重开；正式入口继续复用 LevelManager 的标准加载、生命周期和结果链路。 |
| `Mechanism/MechanismSystem.cs`、`MechanismData.cs` | 经本轮确认新增 Anchor 专用事务请求和快照 `AnchorId`；补齐库存、放置冷却、总上限及场景父节点。没有改动 MapManager 内部路线或区域规则。 |
| `Player/` 放置 backend/预览类型 | 将 Anchor ID 交给专用事务接口，并在预览区分可替换与不可替换；不由 UI 创建或销毁机关。 |
| `UI/` 状态源 | 显示真实洞穴人数、等待时间和结果。 |
| `MAP_FirstLevel.asset`、首关配置、正式场景与测试夹具 | 改正守卫点，设首关史莱姆 20、总机关 20；正式 `FirstLevel` 使用正式地图 Prefab，测试夹具保留独立配置和本地 Manager。 |

- PlayMode：隔离工程副本运行 `-runTests -testPlatform PlayMode`，9/9 通过。覆盖 Bootstrap → MainMenu → `StartFirstLevel()` → `FirstLevel` 的正式入口、正式场景启动、Actor 出生、食物放置并接触后增殖、暂停和原地重开。批处理使用 `-nographics`，这不等于人工可视化或玩家操作验收。
- 未做玩家手动游玩、完整从出生到洞穴的通关录像、真机或正式场景的可视化验收；大尺寸峡谷底图在无图形批处理环境中有纹理尺寸回退提示。保留旧 `Level_test` 及测试场景供兼容回归，未处理已提交且带冲突标记的 `TestScene.unity.meta`。
