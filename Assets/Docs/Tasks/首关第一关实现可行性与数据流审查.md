## 1. 结论摘要

### 1.1 可行性结论

当前项目在架构层面能够承接第一关，但当前仓库还不能直接通过现有 `Level_test` 装配出最新策划要求的第一关。

已经具备、可以复用的基础包括：

- Unity 2022.3.62f2c1 项目、Bootstrap、持久化 `GameRoot` 和 `LevelManager`；
- `LevelContext` 与关卡级 `LevelEventBus` 的生命周期边界；
- `MapManager` 对场景边界、区域、点位、路线和静态阻挡的读取；
- `SlimeManager`、`EnemyManager`、`GuardManager`、`MechanismSystem`、`StatusManager`、`MovementSystem` 的基础运行时骨架；
- Unity Grid 基础坐标转换、网格预览和立即点击放置链；
- 史莱姆、敌人和守卫的基础 Actor/决策/状态/移动代码；
- C# 工程级编译可以通过。

不能直接复用为第一关闭环的部分包括：

- 当前正式场景实际上是旧的、小尺寸 `Level_test` 测试装配，只有一条临时路线；
- 当前 `LevelResultRules` 仍以武器抵达终点、武器损坏和史莱姆耗尽为主要结果输入，没有“进入终点洞穴的史莱姆数量达到 6、等待 10 秒后失败”的规则；
- 第一关策划要求的三条路线、陷阱、补给、教程触发、L/SL 特殊锚点、路线阻断和局部食物预算尚未形成完整生产链；
- 当前放置系统只有普通网格占用，没有 Snap Anchor、特殊点位过滤和替换回收；
- 当前场景中的寒冷/炙热区域与部分状态逻辑仍会触发与“熔炉仅作为引导源、第一关不考虑冷热”相冲突的行为；
- 没有 Unity Editor、PlayMode、人工运行和重开流程的本次实证，因此不能声称第一关运行通过。

### 1.2 当前完成度口径

本次不使用一个容易掩盖阻塞项的总百分比，而按最新第一关的功能组判断：

| 功能组 | 当前状态 | 说明 |

## 3. 最新第一关的需求基线

最新策划将第一关定义为 5760×5760 的俯视 2D 护送/引导关卡：史莱姆从左下方起点出发，玩家通过食物、熔炉、障碍以及路线上的机关影响史莱姆，守卫参与护送，最终至少 6 只史莱姆进入右上/终点洞穴区域；若等待窗口结束仍不足 6 只则失败。

### 3.1 已确认的玩法事实

- 继续使用 Unity，不迁移到 Godot。
- 史莱姆上限为 20。
- 第一关地图包含地形、三条候选路线、主路线、敌人、守卫、史莱姆、食物、熔炉、障碍、陷阱、补给、教程触发和终点区域。
- 守卫不受食物、温暖和史莱姆状态影响；守卫的具体战斗/护送职责仍需与策划的详细行为描述对齐。
- 熔炉第一版仅作为引导源，不触发寒冷或炙热状态。
- 普通放置采用网格放置：地图边界内可放置；普通网格一个格子只允许一个放置对象。
- 特殊点位采用 Unity Grid 与 Snap Anchor 的候选组合；L1/L2/L3 作为路线阻断锚点，SL1/SL2/SL3 作为陷阱缓解锚点。
- 现阶段采用预先设计的固定路线事实，不实现通用动态网格寻路；具体路线选择和阻断时序仍需确认。
- 旧的武器护送链保留为兼容/后续扩展；除非最新策划再次确认，否则不能把它当作第一关当前胜利条件。
- 宠物、通用掉落、通用背包、通用道具和通用事件系统不恢复为本阶段公共系统。若第一关必须有食物预算、怪物死亡掉落食物或补给，则应作为第一关局部规则处理，并在实现前确认边界。

## 4. 当前代码层数据流

### 4.1 启动、加载和关卡生命周期

```text
Bootstrap.unity
  GameRoot(GameRoot + BootstrapMenuLoader)
    └─ LevelManager(LevelManager)
          │ 读取 LevelConfig / Prefab / Build Settings
          ▼
       加载关卡 .unity 场景
          ▼
       创建 LevelContext
          ├─ LevelEventBus        当前关卡独有
          ├─ ConfigRegistry       当前关卡配置快照
          ├─ MapManager           扫描活动场景 authoring
          ├─ StatusManager
          ├─ MovementSystem
          ├─ SlimeManager
          ├─ EnemyManager
          ├─ GuardManager
          ├─ MechanismSystem
          └─ LevelResultRules
          ▼
       场景 MonoBehaviour 收到 LevelStarted
          └─ 绑定父节点、点位、表现层和 Actor Spawner
          ▼
       LevelContext.Tick / FixedTick
          ▼
       LevelManager.ReportResult → UI/场景切换/重开
```

当前代码中的所有权边界如下：

| 对象 | 类型 | 生命周期 | 当前职责 |
| --- | --- | --- | --- |
| `GameRoot` | 挂载在 Bootstrap 持久对象上的 MonoBehaviour | 跨场景 | 创建并持有全局入口 |
| `LevelManager` | 挂载在 Bootstrap 子对象上的 MonoBehaviour | 跨场景 | 加载场景、创建/销毁 Context、暂停/重开、接收结果 |
| `LevelContext` | plain C# | 当前关卡 | 持有关卡模块和事件总线 |
| `LevelEventBus` | plain C# | 当前关卡 | 发布/订阅当前关卡事件，销毁时释放 |
| `MapManager` | plain C# | 当前关卡 | 从活动场景 authoring 建立地图快照和查询 |
| `StatusManager` | plain C# | 当前关卡 | 生命、伤害、治疗、状态效果、击退和移动 Buff |
| `MechanismSystem` | plain C# | 当前关卡 | 运行时机关、食物/熔炉/障碍和旧武器兼容链 |
| `SlimeManager`/`EnemyManager`/`GuardManager` | plain C# | 当前关卡 | Actor 实例、父节点、注册、更新和销毁 |
| `LevelResultRules` | plain C#，位于 Core | 当前关卡 | 聚合事件事实并产生结果；现有规则仍是旧武器规则 |
| `PlacementSystem` | plain C# | 当前放置会话 | 选择、预览、网格占用和放置请求 |
| `FirstLevelPresentationRoot` | 场景 MonoBehaviour | 场景 | 把输入、镜头、网格、选择 UI 和 PlacementSystem 接起来 |

### 4.2 场景 authoring 到运行时快照

当前 `MapManager` 在创建时扫描活动场景中的 authoring：

```text
MapBoundsAuthoring ─┐
MapAreaAuthoring  ──┼─> MapManager.Initialize()
MapPointAuthoring ──┤        ├─ Bounds/Area/Point 快照
MapRouteAuthoring ──┤        ├─ Route 快照
静态 Collider ──────┘        └─ Occupancy/Movement 阻挡查询
```

对于第一关，理想的数据流仍应保持“场景提供事实，运行时系统消费事实”：

```text
场景中的路线/点位/区域/边界/锚点 authoring
  → MapManager 建立不可变或受控快照
  → Actor/Mechanism/Placement/Result 通过公开查询读取
  → 运行时状态变化只通过系统和 LevelEventBus 发布
```

不应让史莱姆、UI 或放置输入直接读取其他系统的私有字段，也不应让场景脚本自行复制一套路线或结果判定。

### 4.3 Actor、状态和移动数据流

```text
LevelActorSpawner(LevelStarted)
  → SlimeManager/EnemyManager/GuardManager
  → 从 Prefab 创建 Actor
  → 注册 MovementSystem
  → 注入 PerceptionSource / ActionPort
  → Actor 决策树/状态机产生动作
  → MovementActorActionPort / MovementSystem 执行动作
  → StatusManager 处理伤害、治疗、状态、击退、移动 Buff
  → LevelEventBus 发布受伤、死亡、状态变化等事件
```

第一关需要在这条链上增加或确认：

- 史莱姆进入终点洞穴的检测归属，以及重复进入是否只计数一次；
- 史莱姆对食物、熔炉、陷阱、敌人和主路线的感知优先级；
- 守卫是否通过独立目标源保护武器/史莱姆/路线，不能因为没有旧武器对象而不生成；
- 陷阱造成的伤害、减速、击退必须经过 `StatusManager` 或已确认的公开状态接口，不能直接修改 Actor 内部生命值/状态；
- 群组数据由史莱姆模块持有，不能由 UI 或场景脚本维护第二份成员列表。

### 4.4 当前放置数据流

```text
InputSystem / InputAction
  → PlacementInputAdapter
      ├─ 判断当前输入模式
      ├─ UI Raycast 过滤
      └─ CameraSystem.ScreenToWorld
  → PlacementSystem
      ├─ Grid.WorldToCell / CellToWorld
      ├─ 边界检查
      ├─ 当前格占用检查
      └─ 生成预览与合法性状态
  → MechanismPlacementBackend
  → MechanismSystem.RequestPlace(configId, position)
  → 创建机制 Prefab / 注册 Collider / 发布机制事件
  → PlacementGridView、SelectionView、HUD 读取结果
```

当前已经存在普通网格坐标转换和“有效点击立即放置”链，但以下第一关数据尚未进入这条链：

- `L1/L2/L3/SL1/SL2/SL3` 的 Anchor 查询和高亮；
- 普通物体与特殊锚点的类型过滤；
- 同位置替换前旧障碍的回收；
- 新障碍创建失败时保留旧对象；
- 受陷阱缓解锚点影响的运行时效果；
- 放置对象进入重开/失败/结算时的统一清理。

### 4.5 最新第一关目标结果的数据流候选

以下是应当实现的目标数据流，但事件名和具体拥有者在实现前仍是待确认的公共接口：

```text
终点洞穴区域/触发检测
  → 识别进入的 SlimeActor
  → 关卡内去重并累计 reachedSlimeCount
  → 发布 SlimeReachedGoalEvent（候选）
  → Core/LevelResultRules 聚合
      ├─ count >= 6       → LevelSucceeded（候选）
      ├─ 进入等待窗口    → LevelWaitWindowStarted（候选）
      └─ 10 秒后仍不足 6 → LevelWaitWindowExpired / LevelFailed（候选）
  → LevelContext 产生结果
  → LevelManager.ReportResult
  → UISystem/HUD 显示结果
  → 暂停输入、结算、重开或返回菜单
```

这是对现有“Core 负责结果规则、武器归 MechanismSystem”的架构方向的延伸，不是要求立即新增这些 API。正式实现前需要确认：终点检测是 `MapManager`、独立的目标区域组件，还是由 `SlimeManager` 查询；以及等待窗口由 `LevelResultRules` 还是单独的 Core 组件持有。

### 4.6 当前 Tick 顺序的冲突

当前 `LevelContext.Tick` 主要执行：

```text
StatusManager → MechanismSystem → MovementSystem.SyncPositions
→ SlimeManager → EnemyManager/GuardManager → LevelResultRules.EndFrame
```

最新策划给出的第一关顺序是：

```text
输入/放置 → 陷阱 → 敌人 → 守卫 → 史莱姆 → 群组
→ 补给/障碍 → 教程 → 关卡流程 → HUD
```

两者不是简单的名称差异：它们会影响同一帧内食物、陷阱、伤害、死亡、到达终点、放置和胜负的先后关系。应在实现前确定采用以下哪一种：

- 保留现有系统 Tick，由第一关局部适配器把新规则接入事件边界；
- 为 `LevelContext` 增加显式阶段调度，使策划 Tick 顺序成为可测试的关卡时序；
- 将部分行为改为事件队列，在固定的 EndFrame 统一提交。

本文不替用户冻结其中一种。

### 6.3 建议的初始化顺序

```text

8. 运行时按确认过的 Tick 阶段执行，并通过事件/快照向 UI 提供数据。
9. 结果产生后，LevelManager 统一暂停、结算、重开或返回菜单。
10. 重开/卸载时销毁 LevelContext、EventBus、Actor、机制、临时 UI 和放置占用。
```

## 7. 关键冲突、阻塞与边界

### 7.1 坐标尺度

最新策划给出 5760×5760 和一组像素坐标；当前 `Level_test` 使用小尺度世界。这里有三个合理方案：

| 方案 | 做法 | 优点 | 风险/后续影响 |
| --- | --- | --- | --- |
| A | Unity 直接采用 1 Unity unit = 1 策划像素 | 坐标直译，调试对照简单 | 大世界相机、碰撞、Prefab 尺寸、性能和美术资源需要全部适配 |
| B | 保留 Unity 小尺度，增加“策划像素→Unity 世界”显式坐标转换 | 兼容现有物理/Prefab 和相机数值 | 所有坐标、半径、速度、UI 标尺必须统一走转换，不能散落除法 |
| C | 按区域分块/流式缩放 | 适合长期大型地图 | 复杂度最高，超出第一关首轮装配范围 |

**建议**：在不迁移引擎的前提下，优先评估 B；但必须先由用户/策划确认单位策略。当前不能把 A 或 B 直接写入生产配置。

### 7.2 正式场景组织

| 方案 | 做法 | 优点 | 风险/成本 |
| --- | --- | --- | --- |
| A | 直接扩展 `Level_test` | 迁移文件少 | 测试夹具、旧冷/热区域和第一关内容混在一起，回归困难 |
| B | 新建独立 `FirstLevel.unity`，保留 `Level_test` 为测试场景 | 正式内容和测试内容边界清楚 | 需要重新装配、登记 Build Settings 和配置 |
| C | 独立正式场景 + `SystemsRoot/LevelSceneInstaller` 负责场景事实接入 | 可维护性和后续多关卡扩展较好 | 需要先确认 Installer 不越权，并增加安装器测试 |

**建议**：以 B+C 作为候选方向，即独立正式场景、保留 `Level_test`，并使用职责受限的场景装配组件；这只是建议，得到确认前不创建正式场景或 Installer。

### 7.3 局部食物预算与“通用系统放弃”的边界

最新第一关详细规格仍写有初始食物预算、补给和怪物死亡后食物相关规则，而此前已经确认暂时放弃通用掉落、背包、道具和事件系统。

可选解释：

- **局部规则**：在第一关 Context/Mechanism/关卡配置内实现 `FoodBudgetState`、S1/S2 和必要的死亡奖励，不恢复通用 Inventory/Drop/Item 系统；
- **简化规则**：只保留场景初始食物，不实现预算/掉落/补给，开发量低但不满足最新详细规格；
- **恢复通用系统**：重新建立通用背包/掉落/道具，扩展性更强但超出当前已确认范围。

**建议**：若策划确认第一关详细规格中的预算和补给必须保留，采用第一种局部规则；不要因为第一关临时需求恢复整个通用系统。仍需用户确认这一边界。

### 7.4 结果规则所有权

当前已经确认的方向是：武器由 `MechanismSystem` 拥有，武器死亡通过关卡事件总线发布；结果规则放在 Core，而不是让 `MechanismSystem` 判断全部胜负。

对于最新第一关，仍需决定以下细节：

- 终点计数由终点区域/Map 模块发布事实，还是由 `SlimeManager` 依据区域查询发布事实；
- `LevelResultRules` 是否继续作为 Core 下的轻量 plain C# 组件；
- 等待 10 秒由结果规则持有，还是单独的关卡流程/计时器持有；
- 旧武器结果事件是否只保留兼容测试，还是在第一关以可选规则启用。

本审查推荐继续保留轻量 Core 结果聚合，不建议让 `LevelManager` 直接读取史莱姆/武器内部状态；但不在本次冻结事件名和类名。

### 7.5 路线阻断和同帧顺序

最新策划明确了 L 锚点用于路线阻断、SL 锚点用于陷阱影响，但没有把所有下列细节定义到可直接编码的程度：

- 玩家什么时候可以选择/改变路线；
- 放置 L1/L2/L3 后，已经在路线上的史莱姆如何处理；
- 路线阻断是阻止新进入、改变引导源，还是触发回退；
- 同一帧同时发生陷阱、放置、敌人攻击、史莱姆死亡和到达终点时的优先级；
- 三路线的选择是否只发生一次，还是允许后续切换。

这些问题必须在实现前向策划确认；固定路线不等于这些时序已经确定。

## 8. 按依赖排序的实施计划

### 阶段 A：前置确认

必须先确认：

1. Unity 对策划坐标的单位/缩放策略；
2. 正式第一关采用独立场景，还是在 `Level_test` 上迁移；
3. `LevelSceneInstaller` 是否采用，以及它只做哪些装配工作；
4. 局部食物预算、补给、怪物死亡食物奖励是否属于第一关必做内容；
5. 终点计数和 10 秒等待窗口的所有权与事件边界；
6. L/SL 锚点的公开查询、放置替换和路线阻断时序；
7. 最新策划中史莱姆不同状态的行为优先级；
8. 是否在第一关继续装配旧武器，还是完全作为兼容测试保留。

### 阶段 B：数据契约与可测试核心

依赖阶段 A 后再做：

- 第一关地图配置和坐标转换策略；
- 三条候选路线 + 主路线的运行时快照；
- 起点、分叉、汇合、终点洞穴和进入去重事实；
- 史莱姆数量上限、食物/局部预算规则；
- 终点计数、等待窗口和结果聚合测试；
- Anchor 查询、类型过滤、占用和替换回收测试；
- 陷阱/补给/教程事件的数据契约测试。

这一阶段不应修改正式场景，也不应把未确认事件名写进全局 API 表。

### 阶段 C：第一关运行时模块

依赖阶段 B 的数据契约：

- 第一关局部食物、补给和障碍行为；
- 陷阱伤害/减速/击退/冷却，并通过 `StatusManager` 进入 Actor；
- 三路线选择/阻断与固定路线移动；
- 史莱姆起步、增殖、分组、终点计数；
- 守卫独立于旧武器链的生成和行为接入；
- 教程触发状态和 HUD 数据快照；
- 结果规则和等待窗口；
- 暂停、失败、CLEAR、SETTLE、重开清理。

### 阶段 D：场景装配

依赖阶段 C 的 authoring/API 稳定后：

- 创建/确认正式第一关场景；
- 装配 5760 坐标或转换后的边界、地形和碰撞；
- 装配路线、点位、敌人、守卫、终点区域；
- 装配食物、熔炉、障碍、陷阱、补给和教程；
- 装配普通 Grid 与 L/SL Snap Anchor；
- 连接 `SystemsRoot` 场景装配组件；
- 连接 Camera/UI/放置选择面板；
- 更新 Build Settings，但必须在场景内容确认后执行。

### 阶段 E：跨系统联调

按以下顺序联调，避免一次同时引入所有不确定性：

1. 只跑地图边界、路线、起点/终点和相机；
2. 加入 1 只史莱姆和守卫，验证移动/碰撞/目标；
3. 加入食物与增殖，验证上限 20；
4. 加入敌人和伤害，验证 `StatusManager`；
5. 加入 T1-T5 陷阱和 SL 锚点；
6. 加入 L 锚点和路线阻断；
7. 加入普通网格放置、障碍耐久/回收/替换；
8. 加入补给、教程、HUD 和结果等待窗口；
9. 最后验证完整 CLEAR/失败/重开/结算。

### 阶段 F：验证门槛

每个阶段必须区分以下证据：

| 验证层级 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 静态 YAML/Prefab/配置审查 | 引用、层级、序列化字段和 Build Settings 是否存在 | 运行时初始化、碰撞和玩家体验 |
| C# 工程编译 | 代码引用和语法可编译 | Unity 场景装配和运行结果 |
| Unity Console/Editor 检查 | 序列化、启动异常和对象实例化日志 | 完整玩家流程 |
| EditMode 测试 | 纯 C# 规则、坐标、占用、结果聚合 | Unity 物理、真实场景和输入 |
