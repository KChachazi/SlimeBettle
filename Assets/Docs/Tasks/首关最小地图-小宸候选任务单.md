# 首关最小地图候选任务单：小宸

状态：候选分工，待用户确认后生效
依据：`Assets/Docs/SlimeBettle设计文档-3.docx`、`项目架构.md` 0.5、`21-InputSystem.md`、`22-PlacementSystem.md`、`23-CameraSystem.md`、`24-UISystem.md`
目标：完成网格放置状态、网格可视化和首关最小 UI 适配，不负责机关/地图/Actor 内部规则

## 1. 任务目标

为首关提供玩家通过环境引导史莱姆的最小交互：

- 选择食物、熔炉或障碍三种机关；
- 进入放置状态时显示独立 `PlacementGridView`，退出时隐藏；
- 屏幕坐标经 `CameraSystem.ScreenToWorld` 转为世界坐标，再通过 Unity Grid 或等价 Grid Authoring 吸附到格子；
- 地图边界内默认合法，一个格子只允许一个玩家放置对象；
- 空闲格子、已占用格子和越界格子有可辨识的预览状态；
- 确认结果交给 `MechanismSystem`，UI 不直接创建机关、不修改 Actor；
- HUD 显示史莱姆数量、护送武器状态、当前结果和放置提示；
- 首关不加入背包、掉落物、独立玩法事件或通用道具系统；仍可消费 `LevelEventBus` 的结果事实事件。

## 2. 前置依赖

1. 使用 `CameraSystem` 的屏幕/世界坐标转换和 `MapManager.TryGetMapBounds(...)`；
2. 使用 `PlacementSystem` 的放置模式、预览和确认边界；
3. 使用 `MechanismSystem` 的公开放置/激活请求和只读机关快照；
4. 使用 Core 结果规则组件的只读结果快照或 `LevelSucceededEvent` / `LevelFailedEvent`；
5. 使用 `InputSystem` 的 PrimaryAction、PointerMoved、Cancel 和生命周期取消事件；不重新解释成直接 Actor 控制。

Grid 原点、单元尺寸、坐标轴方向和放置确认后的连续/单次模式仍需在策划草图与接口评审后确认。任务单只固定“网格 + 单格一个对象 + 边界内默认合法”。

## 3. 允许修改的目录

- `Assets/Game/Scripts/Player/`
- `Assets/Game/Scripts/UI/`
- `Assets/Game/Tests/PlayerPresentation/` 或其他独立测试夹具目录
- 任务需要的 UI/网格测试 Prefab；不得直接修改正式场景引用

## 4. 不允许修改的目录或资产

- `Assets/Game/Scripts/Mechanism/`：不改机关内部运行时和武器所有权；
- `Assets/Game/Scripts/World/`：不改地图边界、地形和固定路线内部实现；
- `Assets/Game/Scripts/Actors/`、`Assets/Game/Scripts/Status/`：不改史莱姆、守卫或状态规则；
- `Assets/Game/Scripts/Core/`：不改 LevelContext、LevelManager 或结果规则组件；
- `Assets/Game/Scenes/Level_test.unity`、Bootstrap、MainMenu 和其他正式场景；
- `ProjectSettings/EditorBuildSettings.asset`。

## 5. 公开接口边界

只能通过公开接口协作：

- `InputSystem.ReadSnapshot()`、输入事件和模式切换；
- `CameraSystem.ScreenToWorld(...)`、`WorldToScreen(...)`、边界设置；
- `MapManager.TryGetMapBounds(...)`；
- `PlacementSystem.BeginPlacement(...)`、`PreviewPlacement(...)`、`ConfirmPlacement()`、`CancelPlacement()`；
- `MechanismSystem.RequestActivate(...)`、只读机关快照和 `PlacementConfirmedEvent`；
- Core 结果规则组件的只读结果快照和最终结果事件。

不要读取 MapManager、MechanismSystem、LevelContext 或 Actor 的私有字段；不要让 UI 直接改格子占用、机关对象、武器生命或关卡阶段。

## 6. 交付物

1. Grid 配置/坐标转换与 `PlacementGridView`；
2. Food / Furnace / Obstacle 三种机关选择和放置模式状态；
3. 空闲、已占用、越界三类预览反馈；
4. 确认、取消、暂停、重开、结算和场景销毁时的清理；
5. 最小 HUD：史莱姆数量（上限 20）、护送武器状态、当前提示、成功/失败结果；
6. 不依赖正式场景的输入、坐标投影、格子吸附和生命周期测试；
7. PR 描述中的静态检查、EditMode/PlayMode/人工运行验证记录和未验证项。

## 7. 验收标准

- 进入放置模式时网格可见，退出、取消、暂停、结算和重开时网格与预览清理；
- 指针移动得到稳定的世界坐标和格子坐标，预览不会随 UI 文本或镜头显示误差漂移；
- 边界外和已占用格子不能确认，边界内空格可以进入确认流程；
- 确认只提交公开机制请求，成功/失败通过 `PlacementResult` 或事件反馈；
- 选择面板不实现背包数量、掉落物、道具库存或熔炉温度状态；
- UI 不把开发测试夹具的模拟结果当成正式胜负判定；
- 不修改正式场景、Build Settings 或其他系统内部代码。

## 8. 并行和合并顺序

- 可与小智的地图查询测试并行，但必须使用公开地图边界 API；
- 依赖小茶确认 MechanismSystem 的放置请求和快照格式后再做正式适配；
- 合并建议：Input/Camera/Grid 单元测试 → Mechanism 放置契约 → Placement/GridView → HUD 与结果适配 → 首关场景装配；
- 测试场景放在 `Assets/Game/Tests/`，不得把测试点击标记、调试按钮或临时对象写入正式场景。

## 9. 必须回报的问题

- Grid 原点、单元尺寸和场景作者配置方式；
- 确认一次后是否继续保持当前机关选择；
- 三种机关是否有首关次数/冷却/总上限；
- 放置预览是否需要显示碰撞体积；
- 路线格子上的障碍如何处理；
- UI 结果事件由 Core 组件直接发布，还是由 LevelManager 转发。
