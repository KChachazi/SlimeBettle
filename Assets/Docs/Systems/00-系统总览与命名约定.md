# 00 系统总览与命名约定

版本：0.2 草案  
最后更新：2026-10-08  
适用范围：SlimeBattle-TapTapGamejam 运行时与编辑器代码  
状态：架构暂定，作为后续系统设计文档的索引

## 1. 文档目的

本目录记录可以被多个开发者同时依赖的系统边界、数据所有权和公共接口。每个系统文档只描述该系统对外可见的契约；私有字段、具体算法和未确认的玩法规则不在这里提前锁死。

系统编号是文档和协作讨论用的稳定标识，不要求对应一个 Unity `GameObject`、程序集或单独的 C# 文件。

## 2. 根命名空间

本批次暂定根命名空间为 `SlimeBattle`。项目名中的连字符不能出现在 C# 命名空间中，因此代码中统一使用 `SlimeBattle`，再按职责划分子命名空间。

如果团队决定更换根命名空间，必须在开始编写运行时代码前一次性替换，并同步更新本目录全部文档；当前文档中的命名空间属于架构约定，不代表已经存在对应代码。

## 4. 分层与依赖方向

```text
GameRoot
  └─ LevelManager
       └─ LevelContext + LevelEventBus
            ├─ ConfigSystem
            ├─ ObjectiveSystem
            ├─ MapSystem
            ├─ ActorCore
            │    ├─ SlimeSystem ── DecisionTreeSystem / StateMachineSystem
            │    │    └─ SlimeGroupSystem
            │    ├─ EnemySystem ── DecisionTreeSystem / StateMachineSystem
            │    └─ GuardSystem ── DecisionTreeSystem / StateMachineSystem
            ├─ MovementSystem
            ├─ MechanismSystem / PassageSystem
            ├─ CombatSystem ── StatusManager
            └─ Player / UI / Presentation
```

依赖方向原则：

- 核心流程可以创建和编排系统，但不直接实现玩法规则。
- 配置系统只提供配置，不依赖角色运行时系统。
- 角色系统拥有角色运行时数据；其他系统通过请求和查询使用它们。
- `StatusManager` 处理效果，但不拥有目标角色的最终生命和种类。
- UI、镜头和表现层可以监听结果，但不能成为规则成功的前置条件。
- `LevelEventBus` 只属于当前关卡；它不是 `GameRoot` 的全局消息中心。

## 5. 共享命名约定

### 5.1 类型和成员

- 类型、接口实现类、方法和属性使用 `PascalCase`。
- 接口使用 `I` 前缀，例如 `IEffectReceiver`。
- 私有字段使用 `camelCase`；布尔值使用 `is`、`has`、`can` 或 `should` 前缀。
- 方法名使用动词，例如 `SpawnSlime`、`TryGetMapBounds`、`SubmitEffect`。
- `ID` 统一写作 `Id`，例如 `ActorId`、`LevelId`、`ConfigId`。

### 5.2 数据类型后缀

| 后缀 | 语义 | 示例 |
| --- | --- | --- |
| `Config` | 设计时、通常只读的配置 | `SlimeConfig` |
| `RuntimeData` | 某个运行时对象的本局数据 | `SlimeRuntimeData` |
| `Request` | 请求另一个系统执行动作 | `DamageRequest` |
| `Result` | 请求或动作的执行结果 | `PlacementResult` |
| `State` | 当前可观察状态 | `LevelState` |
| `Snapshot` | 面向查询或 UI 的只读快照 | `PlayerInputSnapshot` |
| `Event` | 已经发生的结果通知 | `SlimeDiedEvent` |
| `Query` | 查询参数或查询对象 | `MapQuery` |
| `Context` | 一次运行或调用的上下文 | `DecisionContext` |

### 5.3 当前统一的领域词

`LevelId` 表示关卡配置或场景的稳定标识；`ActorId` 表示运行时角色实例；`ConfigId` 表示配置资产的稳定标识；`FactionId` 表示阵营；`StatusId` 表示状态效果配置；`MechanismId` 表示机关实例；`GroupId` 表示史莱姆群体实例；`ObjectiveId` 表示关卡目标实例；`WeaponId` 表示护送武器实例。

这些名称优先用于跨系统数据和公共接口。系统内部可以使用更具体的名称，但不能给相同语义重新发明一套命名。

## 6. 系统文档的固定内容

每份系统设计文档必须包含：所在命名空间、建议实现目录、生命周期、职责、不负责的内容、核心数据、公共接口、对外事件、依赖方向、关键不变量、待确认项和验收场景。

公共接口使用 C# 风格的概念签名表达。它们是协作契约，不代表现在必须按该签名立即写代码；参数和返回类型确定后，必须同步更新 `99-全局API查询表.md`。

## 7. 文档状态

- **核心架构**：职责和边界现在就应遵守。
- **玩法待确认**：保留系统位置，但具体接口可能随着策划方案调整。
- **实现待选**：边界明确，内部技术方案还没有锁定。
- **表现待确认**：不阻塞核心逻辑开发，可以使用占位实现。
