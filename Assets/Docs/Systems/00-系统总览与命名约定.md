## 1. 文档目的

本目录记录系统边界、数据所有权、生命周期和跨系统公共接口。系统表示一组有明确职责的规则，不等于必须创建一个同名 Unity GameObject、程序集或 C# 文件。

本版完成三项结构调整：

1. SlimeManager、EnemyManager、GuardManager 和 MapManager 明确作为 LevelContext 持有的关卡级管理器，并各自保留独立设计文档；
2. StatusManager 统一处理生命、状态和移动相关 Buff/Debuff，不再规划独立的战斗系统；
3. 新增 Actors 模块，统一描述 ActorCore、基础感知与决策树、基础状态机、SlimeActor、EnemyActor、GuardActor 和 SlimeGroupActor。

旧的可能架构草稿不再作为协作源。现行边界以本文件、项目架构、项目规范和本目录其他系统文档为准。

## 2. 根命名空间

项目根命名空间统一为 SlimeBattle。项目名中的连字符不能出现在 C# 命名空间中。

Actors 模块使用 SlimeBattle.Actors 及其子命名空间；LevelContext 持有的 Manager 保留按领域划分的命名空间，例如 SlimeBattle.Slimes、SlimeBattle.Enemies、SlimeBattle.Guards 和 SlimeBattle.World。

## 4. LevelContext 组成

```text
GameRoot
  └─ LevelManager
       └─ LevelContext + LevelEventBus
            ├─ ConfigSystem
            ├─ MapManager
            ├─ SlimeManager ── SlimeActor / SlimeGroupActor
            ├─ EnemyManager ── EnemyActor
            ├─ GuardManager ── GuardActor
            ├─ MovementSystem
            ├─ StatusManager
            ├─ ObjectiveSystem
            ├─ MechanismSystem / PassageSystem（待决定）
            └─ Input / Placement / Camera / UI / Presentation
```

Manager 是 LevelContext 的组成部分，但仍然是独立模块：LevelContext 负责创建、连接、暂停和销毁；Manager 负责自己的集合和领域规则；Actor 负责自己的个体运行时数据和自主行动。

## 5. Actors 模块边界

Actors 模块内部的结构是：

```text
ActorCore
  ├─ ActorDecisionTree + Perception
  ├─ ActorStateMachine
  ├─ SlimeActor
  ├─ EnemyActor
  ├─ GuardActor
  └─ SlimeGroupActor
```

- DecisionTree 负责感知和选择行动意图；
- StateMachine 负责行动执行、攻击时机、暂停和中断；
- AttackAction 在命中时机生成 EffectRequest；
- StatusManager 负责生命和状态变化；
- MovementSystem 负责位置变化和碰撞；
- Manager 负责 Actor 的创建、索引、驱动和销毁。

决策树不能直接扣血，动画回调不能直接造成伤害，Actor Manager 不能维护生命和状态的第二份可写副本。

## 6. StatusManager 与攻击行为

本项目不建立独立的 CombatSystem。攻击是 Actor 的一种行动：

```text
Perception
  → ActorDecisionTree
  → AttackIntent
  → ActorStateMachine / AttackAction
  → StatusManager.ApplyEffect
  → 目标 Actor 生命或状态变化
```

治疗、自残、持续伤害和机关伤害可以直接向 StatusManager 提交 EffectRequest，不需要经过攻击行为。

StatusManager 管理生命变化、状态持续、移动 Buff/Debuff、控制、击退和效果事件；MovementSystem 通过查询 StatusManager 的 MovementModifierSnapshot 执行实际移动。

## 7. 共享命名约定

### 7.1 类型和成员

- 类型、接口、方法和属性使用 PascalCase；
- 接口使用 I 前缀；
- 私有字段使用 camelCase；布尔值使用 is、has、can 或 should 前缀；
- 方法使用动词，例如 SpawnSlime、TryGetMapBounds、ApplyEffect；
- ID 统一写作 Id，例如 ActorId、LevelId、ConfigId。

### 7.2 数据类型后缀

| 后缀 | 语义 | 示例 |
| --- | --- | --- |
| Config | 设计时配置 | SlimeConfig |
| RuntimeData | 单个运行时对象数据 | ActorRuntimeData |
| Request | 请求执行动作 | EffectRequest |
| Result | 请求结果 | EffectApplyResult |
| State | 当前可观察状态 | LevelState |
| Snapshot | 只读查询快照 | ActorSnapshot |
| Event | 已发生的结果通知 | ActorDiedEvent |
| Context | 一次运行或调用上下文 | DecisionContext |

## 8. 系统文档固定内容

每份系统文档必须包含：编号、所在命名空间、建议实现目录、生命周期、职责、不负责的内容、核心数据、公共接口、对外事件、依赖方向、关键不变量、待确认项和验收场景。

公共接口变更时，必须同时更新所属文档和 99-全局API查询表.md。接口表不记录决策树内部节点、状态机内部状态、UI 私有刷新方法和表现播放方法。

## 10. 当前迭代验收重点

P0 先完成以下最小闭环：

```text
加载场景
  → 建立 LevelContext
  → MapManager 提供地图事实
  → SlimeManager 生成 SlimeActor
  → EnemyManager 生成 EnemyActor
  → ActorDecisionTree 感知并产生行动意图
  → MovementSystem 执行移动
  → AttackAction 生成 EffectRequest
  → StatusManager 结算生命或状态
  → ObjectiveSystem 与 UI 读取结果
  → 可以重新加载当前场景
```

第一版不要求一次实现所有史莱姆种类、敌人种类、守卫策略、群体策略和机关规则；但所有新增实现必须遵守上述数据所有权和生命周期边界。
