版本：0.3 草案  
最后更新：2026-10-08  
适用范围：SlimeBattle-TapTapGamejam 运行时与编辑器代码  
状态：架构暂定，作为后续系统设计文档的索引

## 1. 文档目的

本目录记录可以被多个开发者同时依赖的系统边界、数据所有权和公共接口。每个系统文档只描述该系统对外可见的契约；私有字段、具体算法和未确认的玩法规则不在这里提前锁死。

系统编号是文档和协作讨论用的稳定标识，不要求对应一个 Unity `GameObject`、程序集或单独的 C# 文件。

## 2. 根命名空间

本批次暂定根命名空间为 `SlimeBattle`。项目名中的连字符不能出现在 C# 命名空间中，因此代码中统一使用 `SlimeBattle`，再按职责划分子命名空间。

如果团队决定更换根命名空间，必须在开始编写运行时代码前一次性替换，并同步更新本目录全部文档；当前文档中的命名空间属于架构约定，不代表已经存在对应代码。

## 4. 分层与依赖方向

```text
GameRoot
  └─ LevelManager
       └─ LevelContext + LevelEventBus
            ├─ ConfigSystem
            ├─ ObjectiveSystem
            ├─ MapSystem
            ├─ ActorCore
            │    ├─ SlimeSystem ── DecisionTreeSystem / StateMachineSystem
            │    │    └─ SlimeGroupSystem
            │    ├─ EnemySystem ── DecisionTreeSystem / StateMachineSystem
            │    └─ GuardSystem ── DecisionTreeSystem / StateMachineSystem
            ├─ MovementSystem
            ├─ MechanismSystem / PassageSystem
            ├─ CombatSystem ── StatusManager
            └─ Player / UI / Presentation
```

依赖方向原则：

- 核心流程可以创建和编排系统，但不直接实现玩法规则。
- 配置系统只提供配置，不依赖角色运行时系统。
- 角色系统拥有角色运行时数据；其他系统通过请求和查询使用它们。
- `StatusManager` 处理效果，但不拥有目标角色的最终生命和种类。
- UI、镜头和表现层可以监听结果，但不能成为规则成功的前置条件。
- `LevelEventBus` 只属于当前关卡；它不是 `GameRoot` 的全局消息中心。

## 5. 共享命名约定

### 5.1 类型和成员

- 类型、接口实现类、方法和属性使用 `PascalCase`。
- 接口使用 `I` 前缀，例如 `IEffectReceiver`。
- 私有字段使用 `camelCase`；布尔值使用 `is`、`has`、`can` 或 `should` 前缀。
- 方法名使用动词，例如 `SpawnSlime`、`TryGetMapBounds`、`SubmitEffect`。
- `ID` 统一写作 `Id`，例如 `ActorId`、`LevelId`、`ConfigId`。

### 5.2 数据类型后缀

| 后缀 | 语义 | 示例 |
| --- | --- | --- |
| `Config` | 设计时、通常只读的配置 | `SlimeConfig` |
| `RuntimeData` | 某个运行时对象的本局数据 | `SlimeRuntimeData` |
| `Request` | 请求另一个系统执行动作 | `DamageRequest` |
| `Result` | 请求或动作的执行结果 | `PlacementResult` |
| `State` | 当前可观察状态 | `LevelState` |
| `Snapshot` | 面向查询或 UI 的只读快照 | `PlayerInputSnapshot` |
| `Event` | 已经发生的结果通知 | `SlimeDiedEvent` |
| `Query` | 查询参数或查询对象 | `MapQuery` |
| `Context` | 一次运行或调用的上下文 | `DecisionContext` |

### 5.3 当前统一的领域词

`LevelId` 表示关卡配置或场景的稳定标识；`ActorId` 表示运行时角色实例；`ConfigId` 表示配置资产的稳定标识；`FactionId` 表示阵营；`StatusId` 表示状态效果配置；`MechanismId` 表示机关实例；`GroupId` 表示史莱姆群体实例；`ObjectiveId` 表示关卡目标实例；`WeaponId` 表示护送武器实例。

这些名称优先用于跨系统数据和公共接口。系统内部可以使用更具体的名称，但不能给相同语义重新发明一套命名。

## 6. 系统文档的固定内容

每份系统设计文档必须包含：所在命名空间、建议实现目录、生命周期、职责、不负责的内容、核心数据、公共接口、对外事件、依赖方向、关键不变量、待确认项和验收场景。

公共接口使用 C# 风格的概念签名表达。它们是协作契约，不代表现在必须按该签名立即写代码；参数和返回类型确定后，必须同步更新 `99-全局API查询表.md`。

## 7. 文档状态

- **核心架构**：职责和边界现在就应遵守。
- **玩法待确认**：保留系统位置，但具体接口可能随着策划方案调整。
- **实现待选**：边界明确，内部技术方案还没有锁定。
- **表现待确认**：不阻塞核心逻辑开发，可以使用占位实现。

## 8. 当前迭代协作分工

本节是当前三位开发者的系统负责人映射。负责人负责对应系统的实现、测试场景、接口文档和合并前自检；这不代表负责人可以绕过其他系统的公共契约直接修改对方数据。

负责人称呼统一使用项目协作称呼：`小茶`、`小智`、`小宸`。如果系统边界或公共接口发生变化，必须先更新对应系统文档和 `99-全局API查询表.md`，再修改实现。

### 8.1 小茶：核心流程、角色 AI 与目标

| 编号 | 系统 | 当前职责与交付边界 |
| --- | --- | --- |
| CORE-01—CORE-03 | `GameRoot`、`LevelManager`、`LevelContext` / `LevelEventBus` | 维护应用和关卡生命周期、重开清理、本局事件总线以及场景加载入口；当前实现已经完成，后续负责兼容性维护。 |
| DATA-01 | `ConfigSystem` | 建立最小配置读取和校验流程；维护 `ConfigId` 与 ScriptableObject 配置的公共约定，不替其他系统保存运行时数据。 |
| ACTOR-01 | `ActorCore` | 维护角色身份、阵营、实例 ID 和跨系统角色快照。 |
| AI-01—AI-02 | `DecisionTreeSystem`、`StateMachineSystem` | 维护 AI 基础运行契约；决策树负责感知和选择意图，状态机负责执行、暂停和中断，具体角色规则由角色系统接入。 |
| ACTOR-02—ACTOR-05 | `SlimeSystem`、`EnemySystem`、`GuardSystem`、`SlimeGroupSystem` | 维护史莱姆、敌人、守卫及史莱姆群体的运行时数据、生成销毁和行为接入；个体生命归角色系统所有，群体数据归 `SlimeGroupSystem` 所有。 |
| CORE-04 | `ObjectiveSystem` | 维护关卡目标、护送武器状态和成功/失败结果；第一版可以先实现测试目标，但测试规则必须与最终策划规则区分。 |

主程还负责跨系统接口的最终一致性检查和核心测试场景的整合。其他负责人需要的角色查询、效果请求、目标结果等公共数据，由主程通过文档和 API 表明确提供。

### 8.2 小智：地图、移动与战斗

| 编号 | 系统 | 当前职责与交付边界 |
| --- | --- | --- |
| WORLD-01 | `MapSystem` | 读取当前关卡的地图边界、出生点、目标点、可占用区域和空间查询结果；不决定角色为什么移动。 |
| WORLD-02 | `MovementSystem` | 执行移动请求，处理阻挡、接触和移动完成/失败结果；不直接修改 AI 决策，也不直接处理伤害。 |
| COMBAT-01—COMBAT-02 | `StatusManager`、`CombatSystem` | 管理攻击请求、命中判定、伤害与状态效果结算，并将最终效果提交给目标所属系统；不直接拥有史莱姆、敌人或守卫的最终生命。 |

小智负责保证 `MapSystem`、`MovementSystem` 和战斗系统之间的数据一致，但不得绕过角色系统直接写入史莱姆、敌人或守卫的最终生命、状态和 AI 节点。战斗命中后必须通过 `StatusManager` 结算，再由目标所属系统完成最终数据修改。

### 8.3 小宸：玩家输入、放置、镜头、UI 与表现

| 编号 | 系统 | 当前职责与交付边界 |
| --- | --- | --- |
| PLAYER-01 | `InputSystem` | 使用新版 Unity Input System Package 读取设备输入，并转换为设备无关的语义输入；不直接移动角色或创建机关。 |
| PLAYER-02 | `PlacementSystem` | 管理物品选择、世界坐标转换、预览、合法性检查、确认和取消；确认成功后向 `MechanismSystem` 提交放置请求。 |
| PRESENT-01 | `CameraSystem` | 管理镜头移动、缩放、边界和屏幕/世界坐标转换；不决定关卡规则。 |
| UI-01 | `UISystem` | 读取系统快照并显示目标、放置状态、提示、暂停、成功/失败和重开入口；用户操作只转换为系统请求。 |
| PRESENT-02 | `PresentationSystem` | 订阅已发生的玩法结果并驱动占位动画、特效、音效和视觉反馈；表现失败不能回滚玩法结果。 |

小宸负责保证输入、放置预览、镜头和 UI 在同一套语义接口上协作。UI 和表现层不得直接修改 `SlimeRuntimeData`、`WeaponRuntimeData` 或其他系统的私有字段。

### 8.4 未决定系统：MECH-01 与 MECH-02

`MechanismSystem` 和 `PassageSystem` 暂不分配负责人，也不把当前系统文档中的机关、放置物、窄路和排队规则视为已经确定的玩法要求。它们的命名空间和文档暂时保留，是为了避免未来重新整理系统编号；具体职责、接口和实现顺序等策划方案明确后再决定。

在此之前，`PlacementSystem` 只保留输入与预览层的架构位置，不得自行假定某种机关类型，也不得直接创建正式玩法对象。

### 8.5 当前迭代的交付优先级

负责人分配不等于所有系统都必须在同一时间完成。为了先形成最小可玩闭环，本迭代按以下顺序交付：

**P0：必须先跑通的核心闭环**

`CORE-01—CORE-04` 的最小流程、`DATA-01` 最小配置、`ACTOR-01`、`AI-01—AI-02`、`ACTOR-02`、`ACTOR-03`、`WORLD-01—WORLD-02`、`COMBAT-01—COMBAT-02`、`PLAYER-01`、`PRESENT-01` 和 `UI-01` 的占位实现。

P0 的验收链路为：加载关卡 → 生成角色和敌人 → 玩家输入产生移动或战斗操作 → `CombatSystem` 判定命中 → `StatusManager` 结算效果 → `ObjectiveSystem` 判定结果 → UI 显示 → 可以重新加载当前场景。

**P1：核心闭环稳定后的扩展**

`ACTOR-04`、`ACTOR-05` 和 `PRESENT-02` 的完整规则，以及未来确定后的机关、窄路、群体战斗和正式表现。

本轮优先构建“一个敌人 + 一种攻击 + 一种伤害/状态 + 一个成功或失败条件”的战斗切片；不应因此提前实现所有敌人、守卫、状态和群体策略。

### 8.6 负责人之间的交付接口

- 小茶向小智提供角色身份、目标接收效果和战斗配置所需的公共类型；小智负责攻击/效果流程，但不直接修改目标所属系统的私有生命数据。
- 小智向小宸提供地图边界、移动结果和战斗结果查询接口；小宸不复制地图或战斗规则，也不在输入阶段修改正式运行时数据。
- 小宸向小茶提交玩家语义指令；放置请求暂不绑定任何正式机关类型，待 `MECH-01` 确定后再接入。
- 角色、机关和战斗系统之间使用查询、命令和结果事件传递信息，不通过读取对方私有字段协作。
- 每位负责人都可以在 `Assets/Game/Tests/` 下建立自己的测试场景；测试场景必须标明依赖和临时规则，不得把测试规则默认为正式关卡规则。
